## Problem

In Rust, `Default::default()` is ordinary value construction.

For a live quantum owner, producing a default value would normally imply real quantum resource effects, for example:

- allocate a fresh qubit;
- prepare `|0>`;
- construct a clean workspace;
- choose a physical/logical initialization convention.

Those are not ordinary zero-cost/default value semantics.

Generic Rust-shaped code such as

```rust
T::default()
```

must not accidentally allocate or prepare quantum hardware/resources merely because `T = Q<...>`.

## Design question

Decide whether live quantum owner types may ever implement a Rust-like `Default` abstraction.

Candidate possibilities:

- `Default` is permanently unavailable for `Q<T>`;
- `Default` is classical/static-only;
- quantum initialization uses explicit `clean` / `init0` / constructors with effect/resource semantics;
- a future resource-factory trait exists but is intentionally not named `Default`.

This issue does not fix the final choice.

## Questions

- Is `Q<Bit>::default()` ever meaningful?
- What about `Q<Unit>`?
- Can generic trait bounds accidentally create quantum resources?
- Is clean initialization an `Iso`, allocation effect, or separate resource capability?
- Should qlinty reject generic `Default` bounds that might instantiate with quantum owners?
- What is the boundary between default **basis data** and default **live quantum ownership**?

## Required invariant

> **Ordinary generic value construction must not hide quantum allocation/preparation.**

## Acceptance criteria

- [x] The `Default` status of live `Q<T>` is explicit.
- [x] Classical/static default values are distinguished from quantum-resource initialization.
- [x] Generic trait resolution cannot silently allocate quantum resources.
- [x] Clean ancilla creation remains explicit in effect/resource semantics.
- [x] `Q<Unit>` is covered explicitly.
- [x] Diagnostics/docs explain why "default quantum value" is not ordinary Rust default construction.
