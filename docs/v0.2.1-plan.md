# 0.2.1 target: shared QPE through code-driven development

Status: **remaining implementation scope moved here by the user on 2026-09-29**.
This continues the original 2026-09-28 shared-QPE plan after the
[0.2.0 foundation release](v0.2.0-plan.md). The four remaining implementation
areas below are deferred, not completed. Product manifests remain at the
0.2.0 foundation version; this document selects a continuation target, not a current version bump.

## Deliverable and scope

Deliver one ordinary `.qli` QPE/QFT definition reused across target widths,
precisions and phase-fixed operations. The selected profile uses `Bits<n>` and
copyable `CBits<m>`, 1 <= n,m <= 8 and n+m <= 16, with ideal dyadic angles through
denominator 256. QPE returns the measured phase and residual target, preserving
the complete instrument on arbitrary reference systems. Keep explicit conversion
to legacy Bit/product interfaces and all existing special-form contracts.
Flat and nested tuples remain distinct under the [type contract](type-system.md).

`CBits<m>` is the adopted measured-bit spelling; bit k carries weight 2^k when
explicitly decoded as an integer. Historical first attempts retain `CWord<m>`;
that spelling is not a supported alias. Desired source remains unimplemented
until the source specification, lowering and independent checking are complete.

Arbitrary basis-type parameters, general Grover/Shor, approximate synthesis,
hardware integration, Python/QIR input/adaptive interop and continuous-parameter
VQE/QAOA are outside this shared-QPE deliverable and retain separate contracts.

## Compatibility prerequisite

Review the entire public change against the shipped 0.2.0 baseline before
implementing the sized-source API. 0.2.1 requires compatible additions, including
Rust AST/IR/evidence and public Lean declarations, source name resolution,
capacities, toolchains and CLI formats. New variants in an exhaustive public
enum or required fields in public structs are breaking even when new source
syntax is additive. Prefer separate successor APIs with explicit finite adapters;
do not extend an existing public enum incompatibly under the PATCH target.

If the complete feature needs a breaking change, select 0.3.0 and document its
migration under [versioning](versioning.md). Do not force an unsuitable API or
weaken a semantic gate merely to retain 0.2.1. The algorithm and proof scope
below is unchanged whichever compatible release boundary is selected.

## Ordered implementation packets

1. **Complete hierarchical semantics and evidence.** Extend the existing Lean
   components to the [selected hierarchical profile](hierarchical-ir-spec.md).
   Establish full-space isometry/unitarity, reconstruct finite leaves from the
   same bound data, and finish call, encoding, compute/uncompute and remaining
   derivation rules. Bind QFT, controlled powers and the full QPE instrument to
   actual circuit structures. Retain explicit transitional Rust-leaf premises;
   a serialized success flag or handle is not evidence. Keep verification shared
   and bounded, without repeat expansion or dense matrices above six-bit leaves.
2. **Connect independent production verification.** Add strict external
   hierarchy decoding/encoding, independently supplied root contracts and
   fresh-process reconstruction. Connect successor APIs and finite adapters;
   explicitly reject unrepresentable reverse conversions and capacity excess.
   Enable each schema only after its pinned theorem, complete artifact/provider
   binding and mutation tests pass. Follow the [Lean migration gates](lean-kernel-migration.md).
3. **Connect sized source and ordinary standard components.** Preserve desired
   source and baseline failures; finish English G020-1 grammar, typing,
   ownership/effects, semantics, lowering, bounds and migration before source
   implementation. After the hierarchy prerequisite, implement explicit static
   natural arguments, `Bits<n>`/`CBits<m>`, finite folds transferring complete
   ownership, explicit axis/layout operations and concretized sized functions
   as static operation arguments. Implement QFT/QPE, preparation and bulk
   measurement as ordinary `.qli` definitions. Recognizing an algorithm name
   must never replace checking its generated circuit.
4. **Connect execution and integrated acceptance.** Execute checked hierarchical
   IR with dyadic angles, shared calls, fresh sampling and actual repeated
   operation counts. Reuse the common source in order finding and a finite
   amplitude-estimation client, then complete H1–H5 and this release's normal
   migration/distribution validation. The mathematical evaluation used in
   component proofs is not yet this reference runtime.

Implemented finite X2–X6 and the experimental component proofs are retained
from 0.2.0. They need regression coverage when integrated, not reimplementation.
The 2026-10-04 JST checkpoint evaluates readiness, not publication.

## Acceptance carried forward

* Reuse the same QPE/QFT source at (n,m)=(1,3),(2,4),(8,8). Compare independent
  mathematical expectations with small-case execution. The maximum case needs
  generation and checking, not exhaustive simulation.
* Check phase, bit/axis order, superpositions, pi/8 and finer angles, residual
  target states, arbitrary-reference correlations, exact scratch cleanup and
  substitutable implementations.
* In a fresh process reject changes to circuit bodies, counts, type trees,
  ports, dependencies, encodings and theorem identities, against an independently
  supplied expected contract.
* Check `Bits<0>` ownership, empty folds, invalid zero-repeat bodies, out-of-range
  indices, cycles/depth and aggregate capacities. Mathematical zero-width type
  formation does not extend QPE's positive-width profile.
* Retain Bell/feedback/reset/discard, RNG failure, retry/exhaustion and atomic
  execution-error checks; integrate them where the new runtime applies.
* Report IR/evidence sizes, generation work, verifier visits and maximum dense
  dimension separately from actual execution counts. Shared verification must
  not expand repeated bodies or construct matrices beyond the finite leaf bound.
* Complete [H1–H5](hierarchical-ir-spec.md#migration-and-implementation-gates) and normal final
  primary/MSRV Rust, corpus/docs, Lean 4.30.0 build/audit and clean distribution
  checks for the actual continuation candidate. Preserve historical test records.

No failed gate becomes a pass through deferral. The full v0.5.0 Soundness
Theorem, v1 Physical Realizability Theorem and later QLT work remain separate
milestones; local theorems required for enabled M2 rules remain mandatory here.

## Code-driven completion and later milestones

Follow [CD-3/CD-4](code-driven-development.md): retain the desired program,
first source, actual diagnostics and repairs, independent semantic oracle and
type-correct wrong program. Name the author burden removed and its replacement
evidence. Compare repairs, duplicated definitions, manual layouts and
generation/checking costs; report these as development observations, not a
controlled model benchmark. Keep the quick reference executable and register
each public standard API with separate implementation, verification and proof
states in the existing ledger. The external corpus remains the same three sources.

M3 then adds reversible predicate DAG synthesis and reusable Grover; M4 adds
reversible arithmetic and Shor using shared QPE; M5 separates costs and
stabilizes public contracts. All V1-C1–C5 and PR-C1–C4 remain required for v1.
