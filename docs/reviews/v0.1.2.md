## Matrix defect and regression boundary

The tagged script returns:

```python
close([[1]], [[1, 0], [0, 1]])  # True
mul([[1, 2]], [[3]])           # [[3]]
add([[1]], [[2, 3], [4, 5]])   # [[3]]
adj([[1, 2], [3]])            # [[1, 3]]
```

The [repaired helpers](../../scripts/check_imaginary_v1_examples.py) require
nonempty rectangular matrices. Addition and comparison require equal shapes;
multiplication requires matching inner dimensions. Adjoint and scaling validate
their input shape, and powers require square matrices and nonnegative integer
exponents, including at exponent zero. Identity construction requires a positive
integer dimension. Violations raise `ValueError` before arithmetic. In
particular, an invalid `close` raises rather than returning false, so a
`not close(...)` negative example cannot pass because its operands are malformed.

Empty matrices are outside these fixtures; a zero-qubit `Q<Unit>` space is
one-dimensional and its 1-by-1 matrices remain valid. The script's numerical
tolerance and valid arithmetic are unchanged. It remains floating-point design
validation, not exact cleanup evidence. Rust's [exact matrix type](../../src/contract/exact.rs)
already checks dimensions, entry counts and multiplication compatibility; this
defect did not affect that checker.

The [14 regression tests](../../scripts/test_check_imaginary_v1_examples.py)
cover both reported reproducers, extra rows/columns in either operand,
ragged/empty inputs, rectangular products and adjoints, scalar matrices, and
identity/power boundaries. Applied to the original tagged helper module,
10 test methods fail; the four valid-arithmetic methods pass. All 14 pass
after the fix. Documentation CI now runs them before the 52 design checks.

## Dense composition is a generalization blocker

For compatible spaces and the **same intermediate encoding**, the premises

```text
U1 E_in = E_mid u1,   U2 E_mid = E_out u2
```

give `(U2 U1) E_in = E_out (u2 u1)` by associativity and substitution. This
mathematical derivation does not require evaluating the composite matrices.
The current [checked-contract API](../../src/contract/mod.rs) implements the
rule but stores the logical meaning as a dense matrix and calls
`next.contract.logical.compose(self.contract.logical, budget)`. Its tensor,
adjoint and control constructors likewise build dense operators; encodings
and their comparisons also use matrix representations.

For n bits, one dense operator has `4^n` entries and the implemented square
product takes `O(8^n)` scalar operations. This is a fundamental representation
limit. Sharing physical evidence or raising the six-bit limit does not solve
it; replacing only one multiplication with a symbolic node would leave other
matrix-expansion paths unresolved.

The source `apply_contract` path also depends on dense checking:
`FunctionEvidence::check_diagnostic` in [function evidence](../../src/contract/function.rs)
constructs both the implementation and specification matrices and compares
them. Generalizing only `CheckedContract::then` would not remove this
whole-function verification bottleneck.

The [R14 scaling prerequisite](../imaginary-v1/requirements.md#scaling-prerequisite-for-r14)
therefore requires symbolic meanings, encodings and checked proof composition
without mandatory whole-operator expansion in the generalized profile. Dense
exact checks remain useful for bounded leaves and regression examples.
Intermediate interfaces, phase, axis order, entry promises, and binding to
actual IR must remain independently checked. Differing symbolic meanings need
explicit equivalence evidence where definitional equality does not suffice.
Size-parametric arithmetic needs reusable derivations rather than truth-table
enumeration. A dedicated proof calculus or Lean-supported proofs may supply
them; a general external prover is not the only possible implementation, and
its connection to emitted IR is itself an obligation. None is implemented by
this patch.

The [first generalized QPE profile decisions](../imaginary-v1/requirements.md#first-generalized-qpe-profile-decisions-required-by-r08r12r14)
must also fix widths, angles, exact/approximate synthesis, independent checking,
and error composition. The current ring is `Z[zeta_8,1/2]`; `exp(i*pi/8)` is a
primitive sixteenth root outside its containing field `Q(zeta_8)`. The width-four
Python QFT check uses complex floating-point numbers and does not certify an
exact QFT4 implementation. Approximate target accuracy never substitutes for
exact auxiliary cleanup.

## Validation claims and their scope

was inspected at the exact baseline commit. All four jobs (`rust`, `rust-msrv`,
`lean`, `docs`) succeeded. The Rust 1.85.0 Linux log totals **259 passed tests**;
Lean's build step and warning-as-error declaration audit both succeeded.
These observations corroborate the review's release-CI claims, without
claiming access to the reviewer's local environment.

The new macOS aarch64 candidate reruns both Rust toolchains with **258 tests
each**. The difference is the Linux-only non-UTF-8 source-root CLI test.
The [0.1.3 validation record](../releases/v0.1.3.md#local-candidate-validation)
also records fresh Lean, script, example and package checks. These validate
the declared finite profile and the listed fixtures, not arbitrary-size
algorithms, compiler soundness, or physical hardware behavior.
