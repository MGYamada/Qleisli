## Problem

In `src/interchange/process.rs`, the ordinary success path reaps the checker with `try_wait()` (lines 151-163). When the `Invocation` guard drops afterwards, `Drop` (lines 12-21) calls:

```rust
kill_process_group(Pid::from_raw(child.id()), Signal::KILL)
```

followed by `kill()` and `wait()`.

Once the leader has been reaped, its PID/PGID is only reserved while some member of the group is still alive. If the group is empty, the number can be reused. If the reused PID becomes a group leader (`setsid`/`setpgid`, for example a shell job or a daemon started concurrently by the host), the deferred `SIGKILL` reaches an unrelated process group.

The window is small, but the consequence is severe. The library also runs inside long-lived hosts such as the Python client, so it is not limited to short CLI invocations.

#343 (descendant cleanup, closed) and #268 (non-Unix containment) do not cover this ordering issue.

## Proposal

Send the group signal only while the PGID is guaranteed reserved, which is while the leader is unreaped. For example:

- detect exit without reaping (`waitid(..., WEXITED | WNOWAIT)`);
- `kill_process_group` to clean up descendants;
- then reap.

On the timeout or error paths, keep signalling the group before the reap, as today.
