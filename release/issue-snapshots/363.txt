## Problem

On success, `qleisli check` prints `checked source and verified IR: <root>` (`src/bin/qleisli.rs:152`). The wording overstates what the native decision established.

**1. Checker identity.** Any executable that writes the reply framing is reported as having verified the IR. Reproduction with a 5-line stub selected through `QLEISLI_KERNEL`:

```python
#!/usr/bin/env python3
import sys,struct
d=sys.stdin.buffer.read()
r=struct.unpack('<I',d[8:12])[0] if len(d)>=12 else 0
sys.stdout.write("qleisli.qirf-native 1\naccepted\n1\n%d\n" % (1 if r else 0))
```

```text
$ QLEISLI_KERNEL=./stub.py qleisli check bell
checked source and verified IR: bell      (exit 0)
```

Binary identity pinning is tracked in #302 and is out of scope here.

**2. Scope of acceptance.** For an ordinary program with no request or meaning, Lean acceptance establishes:

- graph and structural validity;
- ownership safety (`check_ownershipSafe`);
- the interface check.

It does not establish that the IR preserves the source's meaning. `CLAUDE.md` itself says "Valid output IR alone does not prove source preservation". The unqualified word "verified" invites exactly that reading.

## Proposal

Make the success message, and the corresponding JSON result, state what was established:

- the canonical checker path that authorized the decision;
- whether an independent request or meaning was checked;
- that request-less acceptance covers structure and ownership, not source preservation.

- [x] Output does not use an unqualified "verified" for request-less acceptance.

- [x] CLI tests and documentation updated.
