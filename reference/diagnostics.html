Qleisli Programming Language

Diagnostics and recovery

A diagnostic reports one failed check on a source program, a project or an artifact. It identifies the premise that failed and explains the local rule. Where a correction exists that preserves the intended semantics, the diagnostic describes it. An author starts from the rejected expression and its diagnostic, revises the program, and submits it to the same checker.

A diagnostic describes a failed check. It is not evidence. An accepted handle, a realization claim or a resource claim requires its own successful check on the source or artifact that the claim names.

This chapter covers the diagnostics of the qleisli CLI for edition 2026. It describes the two routes that produce them, their JSON form and their codes. It also gives the guidance that each language boundary offers.

The inference and discovery boundary explains how to find the canonical rule behind a predictable classical mistake.

Routes

The CLI checks source through two routes. The table shows which commands take each one. Both routes use the common checker. They differ in the codes and the locations that they report.

RouteCommands
Project routeqleisli check, run, sample and emit-ir on a source root
Selected-entry routeqleisli check, run, sample and emit-proposal with --entry=MODULE::FUNCTION and --module=NAME=PATH

The sections below state each difference where it applies. A consumer that handles both routes must not assume that one route has the fields or the codes of the other.

The result envelope

A tool that runs a command reads its outcome from one JSON object, the result envelope. With --format=json, a command writes one qleisli.result version-1 object:

FieldValue
format"qleisli.result"
version1
commandThe command name
outcome"ok" or "error"
diagnosticsAn array of diagnostic records
resultThe command’s result, or null when outcome is "error"

Rules:

  • When outcome is "error", diagnostics holds the one error that stopped the command.
  • When outcome is "ok" on the project route, diagnostics holds the warnings of the run, each with severity "warning". It may be empty.
  • On the project route, the process exits with status 2 for the code usage and with status 1 for every other error.

The diagnostic record

Each entry of the diagnostics array is a diagnostic record. A diagnostic record has these fields:

FieldValue
codeA stable category. Codes lists them.
severity"error" or "warning"
messageExplanatory text for the author
primaryThe location of the failure, or null
relatedAn array of related notes

A record may also carry counterexample, ownership_boundary or control_flow_boundary, as Refinements describes.

Use code and the structured fields for automation. Render message for the author. The text output and the JSON output of a command describe the same failed rule.

Rules:

  • A source diagnostic of the project route has an empty related array.
  • An artifact diagnostic, such as one from verify-ir, has primary equal to null. Its related array holds one note whose message is json_pointer: followed by the pointer into the artifact, and whose location is null.
  • A selected-entry diagnostic has an empty related array, or one such pointer note.

Locations

A location names the original source bytes of the failure. Its fields depend on the route.

FieldProject routeSelected-entry route
pathThe file, relative to the source root, with / separatorsThe file, or null
moduleAbsentThe module name, or null
start, endThe half-open byte span in the original sourceThe same
line, columnOne-based coordinates of startAbsent

Rules:

  • line and column count Unicode scalar values. A CRLF pair counts as one line break.
  • On the project route, a file of the bundled standard library has a path that begins with std://.
  • The project route does not report a location whose file has no label relative to the source root. The record then has primary equal to null and the code project.
  • On the selected-entry route, a failure does not always name a file itself. Where it names none, path comes from the --module binding of the module. It is null when neither names one.

Implementation note. The selected-entry loader reports the original byte span of a failure and no line or column. The CLI does not reread the file to compute them.

The project route also reports these codes outside the common checker:

CodeFailure

projectA missing or incompatible manifest, edition or source file

Rules:

  • The project route reports a native setup or transport failure, such as a missing checker executable, with the code project.
  • The selected-entry route applies no such mapping. A missing checker executable there has the code io.
  • Target operations may report unsupported and limit. The command and the reported profile identify the target restriction.

Implementation note. source_error in src/frontend/compile/mod.rs holds the project-route mapping, and v1_code in src/bin/qleisli/json.rs maps setup failures. The conversion from the common checker’s error in src/frontend/specialize.rs merges the three spellings of the selected-entry route.

Refinements

A record can say more than its code and its message. Three optional fields refine a record where the checker identifies the source rule or a concrete witness.

FieldContentRoutes
counterexampleinput_column and output_row, the coordinates of one entry where an exact equation failsProject route and artifact diagnostics
ownership_boundaryboundary is "affine_to_linear"; reason and applies_to are as belowBoth
control_flow_boundaryboundary is "classical_quantum_control"; reason is as belowBoth

The message of a record with a counterexample gives the basis labels and the exact coefficients.

Fieldreason values
ownership_boundaryunresolved_disposal, implicit_quantum_disposal, clean_workspace_return, dirty_workspace_return, computed_workspace_return
control_flow_boundaryif_condition, qif_control, match_selector, qmatch_selector, for_carry, qfor_carry

In an ownership_boundary, the value of applies_to depends on the reason. It is "if_live_quantum_owner" for the reason unresolved_disposal, because the checker inferred no argument type. It is "live_quantum_owner" for every other reason.

Guidance by boundary

The code, the command, the location and the message together identify a failure. The guidance describes the corrections that are available. The table groups the guidance by language boundary. For each boundary, it gives the project-route code first, and the selected-entry code where it differs.

Boundary and codesGuidance
Source form (parse)Show the recognizable local grammar and the original byte span. The guidance for an invented statement such as qlet or qreturn can point to ordinary let and to the tail expression of the block. A rewritten example undergoes the name, type, effect and ownership checks like any other source.
Project and names (project, unknown_name or name, invalid_entry)State which manifest, edition, entry or binding is missing or incompatible. Resolve the declared source identity and use the canonical primitive or checked library path. A derived operation is defined in checked .qli.
Interface and calls (type_mismatch or type, arity, recursive_call or cycle)Identify the required and the supplied interface where available. Regroup a quantum product only when its leaf types and order agree. Thread existing owners through the corrected call or carry. Calls must meet the applicable finite termination rules.
Ownership and access (ownership, capability or access)Identify the live or consumed owner, or the access obligation. Use the owner that the consuming operation returns, or check the premise of the documented access mode and then supply that mode. Preserve linear accounting even for a zero-width owner. An unresolved disposal spelling gets conditional guidance about a live quantum owner.
Workspace return (ownership, contract)Explain the missing return role or the checked restoration equation. Return the clean scratch at zero, restore dirty scratch including its relationship with the reference, or return the owners that with_computed requires for checked uncomputation.
Effects and observation (effect, type_mismatch or type)State the effect of the body or of the callee, and the assertion that it exceeds. For ordinary control on a measurement result, use explicit observation in an observe context. For coherent control, retain the quantum selector, the checked arms and the phase.
Exact equations (contract, invalid_ir)Identify the rejected equation. Where the check yields a concrete witness, show exact coefficients and label input and output in the declared basis order. Investigate phase, axis order and the dependencies of the checked artifact.
Realization eligibility (unsupported, limit)Name the requested target and the failed premise where known. Retain the closed instance and the available source origin. An unsupported synthesis profile or an insufficient target width describes a restriction on realization.
Work and resources (limit)Identify the bound, for example source capacity, exact checking work, or a gate or workspace budget for a target artifact. Use the command and the profile to distinguish these scopes. A checked resource count applies to the artifact that was counted.

An outer construct may add guidance to a diagnostic. It keeps the original cause and location.

See parser and control guidance, effect assertions, ownership and workspace examples and realization diagnostics. The primitive boundary and qrate contracts give the corresponding source and compatibility rules.
