Qleisli Programming Language

Primitive boundary and admission

A language primitive is an operation that the language itself supplies. A program calls it by a bare spelling, such as h or measure_z. Edition 2026 has 13 language primitives. Each one has a typed identity that fixes its typing rule and its effect. A language primitive grants no native acceptance and no general inverse or control capability.

This chapter specifies the source primitive boundary of edition 2026. It covers how the checker looks up a bare spelling, the contract of each primitive and the migration of the 27 retired qualified names. It also covers the ordinary library and the roles of each production path. Its last subject is primitive admission: the reviewed decision to add semantic authority.

Three documents rank above this chapter: the authority hierarchy, TRUSTBOUNDARY.md and STDLIB.md. The inventory of this chapter is a technical classification. It is neither a human adoption of a minimal generating set nor a constitutional interpretation or guarantee. A program reaches an operation through a bare spelling or through an ordinary definition. This form of source access changes neither the meaning of the Raw constructors nor the native acceptance authority.

The project route and the selected-entry route both use the common checker. When a program breaks a rule, the common checker gives the diagnostic a class, such as name. A rule in this chapter names that class. Codes gives the code that each route reports for a class.

The inference and discovery boundary shows where to find a primitive’s contract or inspect a derived definition.

A concrete adapter lowers a checked program to a concrete proposal under fixed capacities. This chapter names two of them. The finite adapter lowers a program to finite Raw IR. The selected adapter prepares a selected entry concretely for the ordinary Raw gate or a dedicated hierarchy gate. The capacities and the supported forms of an adapter are its concrete profile. Status and limits gives both profiles.

Meaning, spelling and implementation

An operation has a meaning, a spelling in source and an implementation. This section keeps them apart. The project separates four categories of meaning. Each category has its own authority and its own obligation.

CategoryAuthority and obligation
Semantic primitive, or irreducible semantic ruleA rule at the independent semantic and checking boundary: an existing operation, instrument, ownership transition or effect rule. Three things about it require review: its intended meaning, its premises and the acceptance that the checker implements. Moving the rule into a backend or a package does not remove these duties.
Language primitiveOne typed PrimitiveId. A program can use its bare spelling only where lexical resolution leaves that spelling unbound and the resolution of ordinary declarations and imports does too. The identity fixes the typing rule and the effect. It grants no native acceptance and no general inverse or control capability.
Derived library definitionOrdinary .qli source that you can inspect. The checker checks it like user source, and its contract is reviewed separately. Its home under std:: grants no privilege.
Backend implementation intrinsicAn implementation of an existing meaning. The target output, the phase, the axes, the workspace and the resources keep their separate preservation and realization obligations. An internal operation tag is not an additional source primitive.

Rules:

  • Only native Lean checking issues a production accepted handle. Parsing, Rust catalogs, lowering, simulation and exporter output issue none.
  • An intended mathematical specification must stay independent of acceptance. It requires specification review.
  • None of these is primitive admission, proof of irreducibility or source preservation: a technical inventory, a refreshed source hash, a successful test.

Bare lookup and ordinary shadowing

A program calls a primitive by writing its name alone. A local binding or a declaration of the program can have the same name, and it then takes the place of the primitive. This section gives the order in which the checker decides what a name refers to.

A bare spelling is an unqualified callable name. An ordinary declaration is a declaration in .qli source, which receives the same checks as user source. The checker looks in four places, in this order, and resolves a bare spelling to the first one that applies:

  1. A lexical binding, whether runtime or static. The checker finds a binding here even when the binding is moved or has the wrong callable category.
  2. An ordinary declaration of the same module, or an ordinary public declaration that the module imports explicitly. The ordinary visibility and collision rules apply.
  3. One of the six original public declarations that the derived prelude supplies, unless the module opts out.
  4. The language primitive with that spelling.

Rules:

  • Resolution is lexical. The checker does not select among overloads by the types of the arguments.
  • A lexical binding determines the use. When that binding has an ownership or category error, the error is final. Lookup never retries a declaration or a primitive of the same name.
  • An ordinary declaration determines the use even when its spelling matches a primitive. Its signature, public effect, access requirements and body obligations apply.
  • A spelling resolves to a primitive only when steps 1 to 3 leave it unbound. A name that no step binds is an error (name).
  • Once lookup has selected a callee, a failed check never selects another callee or another authority. This holds for a failed type, arity, effect, capability, concrete-profile or native check.
  • Parameters, let bindings, fold binders, static providers and restricted classical or basis expressions keep their category and scope rules.
  • A primitive is not an import, a prelude declaration, a reserved identifier or a hidden alias. A program calls h(q) or global_phase_eighth(q) without a use.
  • An ordinary function may have the name h. It receives ordinary source checking, and its name grants no Hadamard meaning. A moved local h shadows both that function and the primitive.
  • The prelude must not reexport a bare primitive spelling (name).
  • A program reaches the ordinary gates and the state and structure definitions through ordinary declarations, imports or qualified references. Six common derived definitions are also in the prelude.
  • The bare name phase_eighth is not an alias of global_phase_eighth. It is an unresolved name (name).
  • A retired qualified path is never a lookup path. Retired qualified names gives its rules.

The checker accepts this program. The ordinary declaration empty_bits determines the use, so the basis body yields the label 1 and not the empty label:

classical fn empty_bits() -> Bit { 1 }
pub isometry fn f(q: Q<Unit>) -> Q<Bit> { basis q as () { empty_bits() } }

The checker rejects this program (type). The local x determines the use, and the checker does not retry the x of the prelude:

observe fn main() -> Bit { let x = 0; measure_z(x(init0())) }

The checker accepts this program. A module that opts out of the prelude keeps the bare primitives measure_z, h and unit:

#![no_implicit_prelude]
observe fn main() -> Bit { measure_z(h(basis unit(()) as _ { 0 })) }

The checker rejects this program (name). After the opt-out, no step binds init0:

#![no_implicit_prelude]
observe fn main() -> Bit { measure_z(init0()) }

tests/frontend_types.rs, tests/selected_coherent_basis.rs and tests/shared_resolution/prelude.rs check these sources.

Implementation note. src/frontend/resolve/locals.rs resolves a lexical binding before any global name. Resolution::lookup in src/frontend/resolve.rs applies steps 2 to 4, and PrimitiveId::lookup_unbound supplies step 4.

Rules:

  • A call must supply the static arguments that the table lists (static-arity) and the number of runtime arguments that it lists (arity).
  • The runtime argument list and the tuple shape of the result are separate. join(a,b) takes two arguments, and unit(()) takes one.
  • Each quantum argument evaluates once, in source order. The call consumes its owner. The primitive returns or eliminates that owner explicitly.
  • Every quantum equation of this section extends to an arbitrary retained reference, on which it acts as the identity.
  • Distinct owners may be entangled. A zero-axis owner is linear.
  • A concrete adapter may refuse an identity that it does not support (unsupported). The refusal does not restore qualified lookup, and it does not replace the source judgment.

The finite and selected adapters consume the same identity. They do not classify a name by its string. Internal tags of the adapters, such as X, Cnot, Init0 and Empty, are transport and emitter vocabulary and have no language identity.

h

h applies the Hadamard gate to one Bit owner: H|b>=(|0>+(-1)^b|1>)/sqrt(2). The result is on the same axis.

Rules:

  • The argument must have type Q<Bit> (type).
  • h keeps, as a primitive rule, the action that mixes amplitudes. A deterministic basis map alone cannot express that superposition.

phase

phase[j,k] applies diag(1,exp(2*pi*i*j/2^k)) to one Bit owner. The static arguments j and k are exact dyadic arguments.

Rules:

  • The argument must have type Q<Bit> (type).
  • The static arguments must pass the coefficient and profile checks of the concrete adapter. Status and limits gives them.
  • phase is a relative phase on a Bit. It is distinct from a scalar.

global_phase_eighth

Let ζ = exp(i*pi/4). global_phase_eighth multiplies the state of one owner by the scalar ζ. Its action is ζ I_A.

Rules:

  • The argument must be one quantum owner of type Q<A> (type). The basis A may be Unit, Bits<0> or a complete packaged tree.
  • global_phase_eighth keeps an explicit scalar phase that has no physical wire.

The checker rejects each of these declarations (type). An ordinary Bit is not a quantum owner, and a tuple of two owners is not one owner:

pub unitary fn f(b: Bit) -> Bit { global_phase_eighth(b) }
pub unitary fn f(q: Q<Unit>,r: Q<Bit>) -> (Q<Unit>,Q<Bit>) { global_phase_eighth((q,r)) }

tests/quantum_unit_source.rs checks these sources.

unit and finish

These two primitives begin and end an owner of type Q<Unit>, which has no axis. unit introduces a fresh zero-axis owner with coefficient +1. finish consumes a zero-axis owner with coefficient +1.

Rules:

  • The argument of unit must have the ordinary type Unit (type). The call unit(()) is unary: its one argument is the value ().
  • The introduction of an owner is an explicit semantic transition. It is not the classical value (), and it is not an implicit preparation.
  • The argument of finish must have type Q<Unit> (type). finish consumes exactly that owner and keeps all preceding scalar work.
  • finish performs no observation. It infers no clean state for another basis.

split and join

These two primitives take a product owner apart and put one together. split partitions one product owner into two owners. join combines two owners into one ordered product owner. Both have coefficient +1.

Rules:

  • The argument of split must have type Q<(A,B)>, a product of two fields (type).
  • split keeps the complete child trees and the left and right axes. It does not flatten implicitly, and it does not promise that the two owners are separable.
  • Each argument of join must be a quantum owner (type). The two owners must be distinct: a second use of one owner is an error (ownership).
  • join(a,b) is a call with two arguments. It is not a call with one tuple argument, and it is not a physical SWAP.

The checker rejects this declaration (ownership). join receives the owner q twice:

pub unitary fn f(q:Q<Unit>)->Q<(Unit,Unit)>{join(q,q)}

tests/quantum_tuple_unitors.rs checks this source.

measure_z

measure_z measures one Bit owner and returns the result as an ordinary Bit. It is the complete destructive Z instrument with the Kraus operators K_b=<b|. It includes every unnormalized reference branch.

Rules:

  • The argument must have type Q<Bit> (type).
  • measure_z consumes the logical owner.
  • A pure label cannot represent the observation. A function that calls measure_z under a unitary or isometry label is an error (effect).

The checker rejects this declaration (effect):

unitary fn f(q:Q<Bit>)->Bit{measure_z(q)}

tests/body_effects.rs checks this source.

discard

A program calls discard to give up an owner explicitly. discard takes the explicit partial trace of one complete subsystem. It keeps the marginal of the reference and every erasure history.

Rules:

  • The argument must be one quantum owner of type Q<A> (type).
  • discard is not a clean release, not a proof of a zero state and not an implicit destruction at scope exit.

take_bit and put_bit

A program uses these two primitives to take one Bit owner out of a register and to put one in. take_bit[n,k] extracts coordinate k of a Bits<n> register and keeps the order of the other coordinates. put_bit[n,k] inserts its first argument at coordinate k and keeps the other coordinates. Both have phase +1. They are the explicit routing and typing rules of an atomic register.

Rules:

  • The static arguments must satisfy k<n (size).
  • The argument of take_bit must have type Q<Bits<n>> (type). A zero-width remainder, as for take_bit[1,0], is an owner.
  • The arguments of put_bit must be two distinct owners of types Q<Bit> and Q<Bits<n-1>> (type).
  • put_bit is not a physical SWAP and not a coercion by width alone.

empty_bits and prepend_bit

These two primitives build ordinary labels. Neither one touches a quantum owner. empty_bits() returns the exact ordinary empty label of type Bits<0>. The label is copyable and has no owner. prepend_bit[n] builds an ordinary label with the head before the tail. It has no quantum action.

Rules:

  • empty_bits takes no runtime argument. The call empty_bits(()) is an error (arity).
  • In a restricted basis or classical expression, only the resolved identity EmptyBits receives the constructor rule. An ordinary function of the same name does not gain it.
  • The arguments of prepend_bit[n] must have the ordinary types Bit and Bits<n> (type).
  • prepend_bit keeps the type rule of a sized label. It is not a preparation and not a measurement.

Effects and types

The effect and the types of a primitive call follow these rules.

Rules:

  • Unitary classifies the quantum action at fixed ordinary inputs. It does not make ordinary copying or dropping a reversible classical computation.
  • Bit, Bits<1>, Unit, Bits<0>, nested and flat tuple trees, and products of separate owners are distinct types.
  • Effect inference checks a body independently of its public annotation. External callers, specialization and provider selection use the public effect.
  • A Unitary or Isometry label must not conceal observation, reset or discard (effect).
  • Unitarity alone grants neither inverse nor control access.

Derivation and removal

A later change can derive a primitive rule in ordinary source, or remove it. These rules constrain such a change.

Rules:

  • A further derivation or a removal of a primitive rule must first express the whole recorded interface in ordinary checked source.
  • It must also provide the applicable independent correspondence. The correspondence covers phase, type, reference, owner and effect, cleanup and resources.
  • A gate identity that holds only up to phase, or a match of widths, is insufficient.
  • The admission process applies to an addition of authority.

  • A retired name is not a callable alias. The four retired namespaces have no callable entry and no compatibility alias. The table preserves the migration and nothing else.

  • A qualified call of a retired name is an error with the same guidance. The project route reports unknown_name, and the selected-entry route reports name.
  • Migration guidance is never a lookup path.
  • A derived replacement has its ordinary public interface and the static arguments that it declares. Replacing an import is not a fallback to the same name.
  • The channel of std::state::reset is rho_AR -> |0><0|_A tensor Tr_A(rho_AR), with a fresh output owner. This formula includes arbitrary reference correlations.

  • A scalar phase accumulated before such a conversion stays in the composition.
  • A pure structural elimination does not invoke discard.

pub unitary fn f(q:Q<Unit>)->Q<Bits<0>>{basis q as () {std::classical::empty_bits()}}

The checker rejects this program. The derived id requires its static argument, as in id[type(Bit)], and the selected-entry route reports static:

observe fn main() -> Bit { measure_z(id(init0())) }

Source retention and resources

These rules state what a call retains from its source and what a resource claim requires.

Rules:

  • An ordinary call retains five things: its original definition, its caller instance, its static arguments, its public effect and its complete source and dependency identity.
  • A checked Meaning override retains the exact original Raw witness, the checked leaf, the matrix, both ports and the reference receipts. An endpoint of the same width or a digest alone is not source correspondence.
  • An original zero-repeat child keeps its checking obligations. A dormant repeat-zero witness is not an equation between an arbitrary hierarchy and a finite implementation.
  • The ordinary preparation std::state::init0 uses the Raw LiftBasis 0-to-1 table [0]. A finite target export must inspect that table and the mapping of the fresh wire and owner. It must not replace an arbitrary rectangular map by an initialization.
  • A structural singleton map retains its complete Unit or Bits<0> tree and its original root. It retains them under composition, repeat, control and adjoint, wherever the concrete profile supports them. Explicit cleanup and the rejected observation, phase and width cases are part of that profile.
  • Source recognition alone enables none of these emitters.
  • Semantic ownership, clean and dirty scratch, and target workspace are separate.
  • The Unit owner in the definition of std::gate::t has zero physical wires. It does not promise that the target T cost is zero.
  • The three ordinary CNOT calls of std::gate::swap differ from the structural output routing of permute_axes, even when a fixed-coordinate matrix agrees.
  • None of these is quantitative Resource Safety: a count of representation sharing, a count of logical instructions, a budget of checker work.
  • Every target or resource claim needs its own artifact, model, units and evidence.
  • Exact cleanup must hold for every permitted input and reference. Approximation never excuses dirty scratch.

Core forms and independent meaning

This section lists the Raw constructors and says where the meaning of the core forms comes from. A Raw constructor is one variant of the public Rust type RawOp in src/ir.rs. RawOp has 22 constructors.

Rules:

  • A Raw constructor is untrusted data. It is not an accepted handle, and the 22 constructors are not 22 library functions.
  • The table is not the entire semantic vocabulary. SingleGate, CircuitAction, protected operations and hierarchy constructors have their own explicit inventories and obligations.
  • An added Raw constructor must pass admission. Calling it an implementation detail does not bypass admission.
  • A source alias does not imply a Raw constructor.
  • RawOp has no free-standing Release0. Clean removal is part of the explicitly checked scope.
  • A reference definition requires human specification review.
  • Lean proves stated relationships to the reference definitions. It does not decide that a chosen formula is the intended gate, instrument or resource model.

Ordinary library and module resolution

The library that comes with the compiler is ordinary source. This section lists its modules and gives the rules by which the imports of a program resolve.

The bundled library is the set of eight ordinary source modules that the compiler embeds under std::. It has 26 public definitions, six transparent prelude reexports and five private helpers. The helpers serve reflection, scalar phase, parameterized phase, packed CNOT and fixed Bit identity.

A loader collects the source modules of a program. The finite loader loads a project from its source root. The selected loader loads modules that are supplied to it explicitly.

  • A bundled module receives the common checks: the declaration, type, owner, access, dependency and effect checks. It has no compiler-import exception.
  • Concrete materialization and native checking occur under the scope of the consumer. Selected source checking alone does not natively certify every bundled specialization.
  • A local module must not have the name std or a name that begins with std::. Both loaders reserve those names for the bundled library.
  • ModuleOrigin::Bundled gives no ambient source replacement and no checking exemption.
  • An unknown path is an error.
  • The resolver registers complete interfaces. It resolves an explicit import with the ordinary visibility and collision rules.
  • A cycle that consists of imports alone is allowed.
  • A self-import is an error. It collides with the declaration of the same module (name).
  • A mutual dependency through a body, a provider, a Basis or a Meaning is an error (cycle). Only a checked decreasing runtime self-call is permitted.
  • Lookup finds a private declaration in its own module. An import from another module and a host entry require a public declaration.
  • An import spelling supplies no runtime initialization and no evidence.
  • The prelude contract admits transparent public reexports. It admits no as, glob or relative import.
  • Resolution, original source identity, concrete materialization and independent acceptance are separate duties.
  • std::routines and std::transforms are retired without aliases.
  • The three fixed arithmetic definitions A001–A003 are ordinary local source in examples/order_finding/arithmetic.qli. They preserve amplitude +1, modular overflow, the addend and the full-space value-15 extension. They have no canonical std export.
  • std::arithmetic is reserved for parameterized arithmetic and number theory. A reserved family name promises no callable API.
  • The English source contracts and STDLIB.md state intended meanings and conventions. Their presence alone does not prove that the implementation conforms.
  • Until version 0.5.0, an algorithm addition ordinarily belongs in the approved corpus, not in an expansion of stdlib. This chapter adopts no library algorithm.

The project route reports every import that fails to resolve with the code project. The selected-entry route reports the class that the rule names.

Implementation note. src/frontend/source.rs::BundledRegistry embeds the eight sources and their fixed manifest. Both loaders retain the complete original sources, their provenance and their original ASTs. Each loader checks the bundled bytes under its own byte policy before it parses or copies them.

Required generic-contract bindings

A generic rule must bind all of the following data. It binds them independently of QFT, QPE or any other algorithm name. The list is a contract for the planned migration to generic rules. It enables no serialized schema and claims no generic completeness.

  1. Original implementation. Retain the original artifact bytes, the complete operation bodies, the selected root, and the checked dependency graph and its order. Bind the called providers, the shared nodes, and the zero-count or otherwise unused obligations that the profile requires. A stale index, an equal name, a matching digest without correspondence, or a native-valid replacement is insufficient.
  2. Complete interfaces. Retain separate domain and codomain type trees, classical result trees, ordered quantum ports, owner identities, wire coordinates, and explicit input and output encodings. Unit, Bit, atomic Bits and product trees are distinct even at equal width. State and check the encoding dimensions, the isometry premises and the entry and exit compatibility. Composition matches the complete intermediate contract, not only its bit count.
  3. Actual semantic action. Check the actual gates, the exact coefficients and phase, the axis order, the controls, the ownership and effect transitions, and the permitted branches. For an instrument, retain every unnormalized hidden history and the ordered public projection. State the premises on arbitrary inputs and references. Distinct owners are not evidence of separability.
  4. Independent expected meaning. Fix the requested meaning before the search for candidates, whether it is a library, operator or instrument meaning. Retain its original definition, its request bytes, its source and specification identity, and its dependencies. The match of a recognizer cannot define it, and neither can a probability table derived from the implementation. Review the intended mathematical meaning separately from the proof of conformance.
  5. Capabilities and workspace. Bind forward, adjoint and control access separately from semantic unitarity. Bind them together with the owners, the effects, the clean and dirty workspace, and the exact restoration premises. A body that observes, resets or discards cannot obtain a pure label by hiding those operations. A resource claim must additionally bind its target, cost model, workspace and artifact.
  6. Actual checking execution. Identify the protocol, schema, profile and checker compatibility separately from the edition and the product version. Retain the original byte decoding, the requested root, the derived obligations and continuous checking states. Where the execution representation that the host retains crosses the Lean boundary, compare the complete representation independently. A serialized success flag or an old receipt cannot replace a fresh decision.
  7. Consumed or emitted artifact. Bind a checked conclusion to the immutable object that execution or emission consumes. A claim about source, runtime or targets requires its own preservation link. Accepting both endpoints independently does not prove a correspondence between them.
  8. Declared domain and failure. State every finite, coefficient and phase limit, every depth and work limit, and every interface limit. A generalization of the phase domain requires its own specification, proof and profile migration. Reject unsupported forms, changed contracts and exhausted budgets without an authority fallback.

Rules:

  • The generic checker may establish a reusable composition or contract rule.
  • A mathematical result that is specific to an algorithm belongs to the library, specification and proof modules that instantiate those rules. The Fourier sum and the QPE distribution are such results.
  • Adding an algorithm must not require granting its name a trusted semantic rule.
  • An intended definition must stay independent of acceptance.
  • QleisliKernel.Qft, Qpe, the hierarchy Fourier and QPE checks, and their lean/Qleisli bridge proofs are implemented, specialized components. The role assignment does not move or delete them.
  • The supported checks, the exact finite contracts, the VM-22–VM-29 authority gates and the existing proof coverage must stay until reviewed replacements cover them.

Admission and replacement process

This section gives the steps of primitive admission. The adopted interpretations require an explicit review before any addition of semantic authority. The decision is recorded in an Issue, and this chapter keeps no second backlog. The account of a proposal must contain all of the following:

  1. Identify the addition. Specify whether it changes semantic rules, exposes an existing rule under a source name, derives checked source, or implements an existing meaning as an intrinsic. List the affected source and Core forms, checker predicates, reference definitions and production paths.
  2. Justify irreducibility. Explain why each of these is insufficient: ordinary checked source, bounded elaboration, a verified transformation, a capability or evidence object, a qrate definition, and target lowering. Performance, popularity, backend availability and implementation difficulty alone do not qualify.
  3. State the independent contract. Give the exact whole-input map or the complete instrument. Give the type and tuple tree, the encodings, the finite domain, the phase, the ordered axes, the owners, the effects, the capabilities and the failure behavior. Include arbitrary permitted inputs and references. A gate name or a probability table is not the contract. State the premises, and do not assume separability.
  4. State workspace and realization obligations. Distinguish semantic data, clean and dirty scratch, and backend workspace. Require exact permitted cleanup and reference restoration. State the target and gate assumptions and the realization correspondence that PR requires. The contract implies no unspecified target schema, no projective quotient and no approximate cleanup.
  5. Analyze QS, PR and RS. Identify the existing binding interpretations and ledger scopes, the changed dependencies and assumptions, and the acceptance and artifact bindings as implemented. State the quantitative measures and the preservation obligations under RS. Ownership checks and checker work budgets do not substitute for them.
  6. Provide production evidence. Check the actual executable definitions, the transport and decoding, and the interface and request binding. Add bounded independent positive and negative cases, as applicable, for phase, axis order, references, wrong effects, duplicate or dropped owners, workspace and stale identities. Build and audit the changed proofs, and retain the explicit source, runtime and target gaps.
  7. Record the decision and migration. Follow the authority hierarchy for specification review, for any constitutional interpretation beyond the adopted ones, and for guarantee admission. An ordinary alias or an implementation choice that the existing interpretations cover does not require a separate Guardian ruling for each edit. Update the reviewed inventories, the compatibility mapping and the applicable proofs before enabling the changed boundary. A manifest edit does not grant approval.

Rules:

  • Project axioms, unsafe or partial executable definitions, and runtime overrides are forbidden.
  • A reviewed physical or semantic assumption must be explicit in the contract. It is not permission to declare a Lean project axiom, and it is not permission to accept an unchecked assertion of a producer.
  • A replacement of an implementation, or the exposure of an equivalent derived definition, must retain the old intended meaning and the applicable guarantees through explicit correspondence.
  • A semantic change must not hide under an unchanged name.
  • Release compatibility and migration are recorded separately from the constitutional edition. Not every primitive edit changes the constitutional regime.
  • A needed constitutional amendment follows the edition procedure of the Constitution.
  • Historical artifacts and records are retained. They must not be rewritten to match the replacement.

Example: a proposal seals qft2 solely because a backend executes it faster. The proposal fails the irreducibility justification, because the ordinary checked std::transform::qft2 expresses its phase-fixed finite contract. An optimization or a target intrinsic can instead propose a realization of that same meaning and supply the required independent checks.

This example assesses the stated rationale. It does not claim that a historical proposal was formally rejected, and it does not claim that the optimization is verified.

Edition-aware deprecation and replacement

These rules govern the deprecation and the replacement of a primitive within an edition and across editions.

Rules:

  • A proposal must distinguish two things: retiring a spelling or an implementation, and changing the meaning of the primitive.
  • It must record the exact source and Core forms before and after the change, the semantic contracts, the profile and API mapping, the release compatibility, and the proof and guarantee dependencies.
  • An equivalent derived replacement needs checked correspondence for the full recorded domain, including phase, references, owners and effects, and workspace. A few matching examples are insufficient.
  • Each historical primitive set must stay recoverable from its exact Git revision and its reviewed inventories, with its original edition, its profile and its applicable meaning.
  • Old manifests and adoption records must not be rewritten to describe a replacement.
  • A later edition may deprecate source access under its explicit migration policy. It must not erase or weaken an accumulated guarantee for its historical scope.
  • Within edition 2026, the evolution of an implementation preserves the old intended meaning. An incompatible source removal requires the ordinary breaking-release process, even when it preserves the safety implication.
  • A changed constitutional regime follows the amendment procedure of the Constitution.
  • Neither an edition increment nor another primitive name waives non-weakening.
