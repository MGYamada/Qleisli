## Status

**Qleisli 0.3.0 important. Priority: highest. Constitutional / toolchain compatibility rule.**

If `std` is an ordinary qrate semantically but is bundled as part of the official Qleisli distribution, its version relationship to the language/toolchain must be fixed now.

Adopt the normative rule:

> **For every official Qleisli release `vX.Y.Z`, the bundled `std` qrate MUST have exactly version `vX.Y.Z`.**

The user chooses a **Qleisli toolchain version**, not an independent standard-library version.

## 1. Exact release-version lock

For an official release:

```text
Qleisli 0.3.0
├── compiler/toolchain 0.3.0
├── verifier/kernel  0.3.0
└── std qrate        0.3.0
```

Likewise:

```text
Qleisli X.Y.Z  <=>  bundled std X.Y.Z
```

The official distribution must not produce states such as:

```text
Qleisli 0.3.0 + std 0.3.1
Qleisli 0.3.0 + std 0.4.0
Qleisli 0.4.0 + std 0.3.0
```

as supported official toolchain configurations.

For prereleases, the same principle should apply to the canonical release identifier.

## 2. Eliminate the Qleisli × std compatibility matrix

The purpose of this rule is not cosmetic version-number synchronization.

It removes an entire compatibility dimension.

Without the rule:

```text
Which std versions work with which Qleisli versions?
```

becomes a permanent compatibility matrix.

With the rule:

```text
choose Qleisli 0.3.0
        ↓
receive std 0.3.0
```

There is exactly one canonical bundled std for each official toolchain release.

## 3. Users do not independently select std

The ordinary qrate manifest should not require users to write:

```toml
[dependencies]
std = "0.3.0"
```

for normal Qleisli programs.

Instead:

> **The active Qleisli toolchain determines the canonical std qrate version implicitly.**

A normal package may declare its own package version and third-party dependencies while receiving the toolchain-matched std automatically.

Conceptually:

```toml
[package]
name = "foo"
version = "0.1.0"

[dependencies]
some_qrate = "1.2"
```

means that `std` comes from the selected Qleisli toolchain, not from an independent dependency choice.

## 4. To select an older std, select an older toolchain

The supported model should be:

> **You do not downgrade or upgrade std independently. You select another Qleisli toolchain.**

For example, if a project requires the 0.3.0 standard library contract, its reproducible environment should select Qleisli 0.3.0 rather than attempting to combine std 0.3.0 with Qleisli 0.4.0.

This keeps language semantics, primitive boundary, verifier behavior, and canonical std contracts aligned.

## 5. `std` remains semantically ordinary

Version locking must **not** be interpreted as semantic privilege.

The distinction is:

```text
semantic status:
    std == ordinary checked qrate

distribution/version policy:
    std == toolchain-coupled distinguished qrate
```

Therefore the version-lock rule is compatible with #167:

- stdlib remains derived `.qli`;
- it receives no verifier bypass;
- it defines no new primitive authority;
- its special status is release coupling and compatibility policy.

## 6. qlirgo must enforce the invariant

qlirgo/toolchain resolution should treat the matching std as part of the selected Qleisli environment.

For official toolchains:

- qlirgo resolves the bundled/matched std automatically;
- explicit mismatched std selection should be rejected;
- the resolved environment should record the effective toolchain/std pair;
- diagnostics should explain that std is selected by toolchain version;
- dependency resolution must not silently replace the canonical std with another version.

The implementation may evolve, but the invariant must not.

## 7. Lockfiles and reproducibility

The lock/build record should preserve enough information to reconstruct the effective environment.

At minimum, reproducibility should make the following pair unambiguous:

```text
Qleisli toolchain version
canonical std qrate version
```

Because the versions are normatively equal, the lockfile may avoid redundant user-facing configuration, but tooling should still be able to verify the invariant.

A stale or manually modified environment with a mismatched pair should fail clearly rather than compiling under an unsupported mixed state.

## 8. Release engineering invariant

Official release automation should enforce:

```text
toolchain_version == std_qrate_version
```

before publishing/releasing.

This should ideally become a CI/release assertion so version drift cannot occur accidentally.

The invariant applies to at least:

- source version metadata;
- bundled std manifest/version;
- release artifact metadata;
- qlirgo/toolchain package records.

## 9. Compatibility policy becomes simpler

The version lock means compatibility statements can be made at the toolchain level:

```text
Qleisli 0.3.0 environment
Qleisli 0.4.0 environment
...
```

rather than separately versioning:

```text
language version
compiler version
verifier version
stdlib version
```

for users as independent choices.

Internal components may still have implementation identities where needed, but the official language distribution exposes one coherent release boundary.

## 10. Relationship to qrate semantics

This issue depends on the companion 0.3.0 qrate-definition flagship:

- qrate defines the general package abstraction;
- `std` is one qrate under that abstraction;
- this issue adds the special **official release-coupling policy** for std.

The key distinction should remain explicit:

> **`std` is privileged in distribution and version coupling, not in semantics.**

## Non-goals

This issue does not require:

- forbidding third-party qrate versions from evolving independently;
- a final public registry design;
- freezing every future std API at 0.3.0;
- preventing internal compiler component versions from existing;
- making std a language primitive.

It fixes only the official toolchain/std release identity rule.

## 0.3.0 acceptance criteria

- [ ] The normative specification states that official Qleisli `X.Y.Z` bundles std qrate `X.Y.Z`.
- [ ] Normal user manifests do not independently select the standard-library version.
- [ ] Selecting a Qleisli toolchain deterministically selects the corresponding std.
- [ ] Supported official configurations reject mismatched Qleisli/std versions.
- [ ] qlirgo records/verifies the effective toolchain/std pairing.
- [ ] Release CI checks `toolchain_version == std_qrate_version`.
- [ ] Reproducibility metadata is sufficient to detect a mismatched or stale std.
- [ ] Documentation states that using an older/newer canonical std means selecting the corresponding Qleisli toolchain.
- [ ] The rule is explicitly described as distribution/compatibility privilege, not semantic privilege.
- [ ] #167 and the qrate-definition flagship are cross-referenced.

## Release principle

> **You choose a Qleisli version; its standard library comes with it.**

Equivalently:

> **One official Qleisli release = one canonical std qrate of the same version.**
