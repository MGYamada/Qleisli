candidate direction, acceptance experiment, checker/dependencies and migration

## Candidates

### A020-01 — Product layout still leaks into composition

**Observed, 0.1.8.** [The rejected call](../tests/fixtures/qli_authoring/rejected/product_association.qli)
and [working adapter](../tests/fixtures/qli_authoring/accepted/product_reassociation.qli)
show manual split/join work around QFT. Flat tuple sugar removes punctuation,
but left, right and balanced trees remain different interfaces.
Investigate register views, aliases or explicit layout adapters without choosing
syntax yet. **Acceptance:** compose QFT and arithmetic clients without hand-written
tree rebuilding at each call; compare against existing adapters, including
entangled inputs, leaf order and zero-width owners. Specify migration and
translation to existing ownership operations; never silently permute axes.

**Reopened design question, user request 2026-09-28:** reassess whether spelling
`(Bit,Bit,Bit)` as the exact type `((Bit,Bit),Bit)` is the right language design
at all. Do not assume left association is the target merely because it matches
the current AST. Mathematical reassociation does not select a unique source
representation, ownership interface or bit encoding.

Compare left-associated sugar, right-associated sugar, and a genuinely flat
source-level n-ary product whose lowering can still use the existing binary
core. Also decide how explicit nested products differ from flat products and
whether any reassociation is explicit or implicit. These are alternatives to
evaluate, not adopted notation or new trusted rules.

Use the same QFT, arithmetic and meaning-contract clients to compare natural
LLM-authored signatures/patterns, required adapters and diagnostic repairs.
Check field/axis order, phase under control, entangled inputs, Unit factors,
linear ownership, and the distinction between `Q<(A,B)>` and `(Q<A>,Q<B>)`.
Include the current right-associated `phase_by` exponent result in migration
experiments. Before selecting a replacement, document source/public-AST/IR
compatibility, meaning-preserving lowering and semantic regressions.

**Decision and implementation, 2026-09-29:** the user selected distinct
arity-preserving tuples. The [type contract](type-system.md) and
[migration](tuple-shapes.md) supersede 0.1.8's left-fold equality. AST, source
types/values/patterns and finite evidence now retain arity; explicit adapters
preserve state/reference correlations, and wrong-shape/meaning cases reject.
The [originally accepted source](../tests/fixtures/tuple_shapes/baseline.json)
is preserved. This closes the equality decision, not every layout/algorithm
ergonomics obligation in A020-01; general register views and sized QPE remain open.

**QFT integration observation, 2026-09-29:** an owner/axis metadata renaming
does not establish that a physical bit reversal ran. The [typed QFT graph
projection](lean-qft-graph-packet.md) therefore retains an actual data permutation
and checks the complete unchanged `Bits(m)` interface separately. The retained
[wrong-reversal source](../tests/fixtures/lean_qft/wrong_reversal/main.qli) and
native wrong-output-order/final-permutation mutations exercise this distinction.
The external hierarchy importer must bind its actual swaps/rewires to that
operation, rather than discharge it with `Layout.PortsMatch` alone. This is an
open importer obligation, not a defect in the existing phase-free renaming theorem.

**Sized-register importer obligation, 2026-09-29:** the desired
[control-routing helper](imaginary-v1/qpe.md#visible-algorithm-and-ownership-routing)
splits `Bits(m)` into `Bit` and `Bits(m−1)` and later joins them explicitly.
The current hierarchy `rewire` preserves each owner slot's exact type; it cannot
justify this split/join or conversion to a legacy tuple by dimension alone.
A bounded six-bit leaf also cannot justify an eight-bit reshaping boundary.
Before source integration, specify and check the explicit structural conversion
(including its inverse, axis order and every zero-width owner), or an equivalent
composition of admitted ownership constructors. Acceptance must cover all eight
selected-axis positions, m=1 with a retained `Bits(0)` remainder, wrong tuple
arity, duplicated/lost owners and entangled reference inputs. This refines the
existing explicit-axis/conversion obligation; it does not adopt implicit type
coercions or change the current `rewire` rule.

**Internal implementation, 2026-09-29:** the
[explicit structural conversion rule](hierarchical-ir-spec.md#explicit-structural-conversions)
now checks Bits/Bit, immediate tuple and empty-owner transitions in both actual
hierarchy typing passes. Both inverse routing laws and arbitrary-reference
coefficient round trips are proved for the executable predicate. The fixture
checks all eight widths and every selected axis. Source lowering, external
semantic evidence binding and the ordinary shared algorithms remain open; the
rule does not introduce implicit conversion or eliminate the source author's
remaining manual work yet.

**0.3.0 design review, 2026-09-29
([#15](https://github.com/MGYamada/Qleisli/issues/15)).** The remaining author
obligation is the monoidal associator itself. By coherence, two bracketings of
the same ordered leaves have exactly one canonical isomorphism. A leaf
permutation, by contrast, changes the operator and must stay explicit.

The language's own interfaces still use three conventions for three bits:
- [qft3](../stdlib/src/transforms.qli) is left-nested;
- the `phase_by` exponent is right-nested (A020-28);
- `toffoli` returns `((c1,c2),t)`, and 0.2.0 now rejects the natural flat
  pattern for that result.

Multi-parameter predicates are also left-folded silently (A020-32).

Decide whether strict shape equality stays. If it does, record its
quantum-semantic or evidence justification. Reversing any part of the 0.2.0
decision is a MINOR change.

### A020-09 — Controlled access can derive inverse access through constructors

**Observed in the supplied 0.1.8 review; retained and tested in 0.1.9
(2026-09-28).** The [M1 constructor table](next-minor-spec.md#access-judgments-and-composition)
and [implementation](../src/frontend/compile/operations.rs) derive Controlled
for `inverse_op(U)` and all three accesses for `controlled_op(U)` from only
`Controlled(U)`. The [non-Hermitian T regression](../tests/operation_parameters.rs)
preserves these accepted cases and rejects direct `U(q)` / `adjoint(U,q)`.
With helpers requiring Controlled, Apply and Adjoint respectively, the minimal
body fragments are:

```text
ctrl[inverse_op(U)](c,q)
apply2[controlled_op(U)](join(c,q))
adjoint2[controlled_op(U)](join(c,q))
```

Preparing c as `|1>` permits u† through
the first/third paths. The regression contains complete source and checks
T† T by interference, so substituting T for T† changes the result.

**Author obligation/design gap:** a header's direct access constraints do not
describe all access derivable through transparent circuit constructors. The
current behavior is sound for M1's checked transparent providers, but cannot
be assumed for opaque providers. The old prose “one does not imply another”
overstated independence; 0.1.9 clarifies direct versus derived access.

**Candidate directions:** retain an explicitly transparent derivation profile,
or require separate inverse-of-controlled evidence and tighten the table.
The latter rejects previously accepted source and requires MINOR migration.
Opaque providers need a separately specified evidence/access interface before
adoption. Mathematical unitarity alone supplies no implementation access.
**Acceptance experiment:** check the complete constructor/access closure for
Apply-only, Adjoint-only and Controlled-only parameters; exercise T/T† and
phase-sensitive entangled controls, absent inverse-of-control evidence and
unused/zero-repeat cases. Any opaque profile must reject missing obligations
at generic-body checking rather than discovering hidden requirements only at
instantiation. Preserve phase, ownership and independent actual-circuit binding.
This entry selects no new semantics; tightening remains open.

### A020-10 — Source snapshot copies exhaust the shared lowering budget

**Resolved compatibly in 0.1.9 (2026-09-28).** The
[F2 resolution](reviews/b019-f2-resolution.md) and
[independent audit](reviews/b019-trusted-audit.md) record the implementation
and validation. The following observation is preserved as historical evidence.
In 0.1.8, each new [provider receipt](../src/frontend/compile/operations.rs) and
[contract pair](../src/frontend/compile/lower/function_contract.rs) copied all
loaded sources into public `FunctionIdentity.sources: Vec<(String,String)>`.
The source bytes spent the same 1,000,000-unit lowering budget as AST/circuit
work, including unimported modules, comments and roughly 7 KB of bundled std.
The original M1 work-unit description omitted this cost. The initial limits
clarification documented the discrepancy without resolving it; the current
[limits contract](next-minor-spec.md#scope-vocabulary-and-limits) now records
the implemented shared-retention repair.

The supplied Linux review reports rejection at the 75th provider for a roughly
6 KB source file and the 38th for an 18.7 KB file. It also reports that 40
providers accepted before adding an unimported, comment-only 25 KB module then
fail with `limit`. These thresholds are reviewer measurements, not guaranteed
capacities; all loaded source bytes and other work affect them. Reproduce with
distinct one-gate unitary providers, each passed to an Apply-only generic helper,
then add the comment-only module without changing any call or import.

The [local B019 replay](reviews/b019-2026-09-28.md#f2-reproduction) on 2026-09-28
confirmed this behavior: a 2,919-byte main with 40 providers passed; adding an
unimported 25,003-byte comment-only module failed with `limit` at `main.qli:75:15`.
The frozen source and both actual JSON results are retained in that record.

**Removed author obligation:** authors had to budget irrelevant text and repeated
snapshot retention to reuse even trivial operations. The 256-specialization cap
did not remove that source-size-dependent burden.
**Alternatives considered:** share one immutable compilation snapshot and charge it
once; separate source-byte retention from lowering work; or restrict snapshots
to the full dependency closure. Replacing the public Vec field with Arc is a
breaking Rust API change requiring MINOR migration. Any alternative must still
bound memory before copying and bind complete source/dependency identity; hashes
or mutable shared storage cannot issue evidence. Consider static providers and
`apply_contract` together, retaining [FC-CACHE](function-contracts-v0.1.md).
**Acceptance experiment:** a 100 KB project with 256 trivial distinct provider
specializations passes; adding an unrelated comment-only module does not change
acceptance. Measure retained bytes and charged work, check cache reuse and
changed-dependency rejection, and test the separately specified storage limits.
These experiments now pass without raising a budget. They are bounded examples,
not a promise that every arbitrary 256-specialization program fits all limits.

**Resolution:** one private immutable snapshot is retained and charged once
across both consumers, with existing storage bounds checked before copying.
The public Vec field and owned inspection API remain unchanged; explicit
inspection lazily materializes one bounded compatibility view per receipt,
shared by its clones. Exact metadata/raw binding, each receipt's exact-check
budget and the 256-specialization limit remain. Five internal unit regressions
measure shared storage/work, limits and inspection; three
[source regressions](../tests/source_snapshots.rs) cover 100 KB plus 25 KB of
comments, 256 providers, 256 contract pairs, mixed consumers and changed
transitive dependencies. The original 40-provider replay now succeeds in both
configurations. The [diagnostic regressions](../tests/repair_diagnostics.rs)
still cover genuine source-retention work failures. Source loading itself
remains the distinct future X6/A020-20 policy task.

### A020-17 — Portable proposals need checking independent of their producer

**0.2.0 implementation:** QIRF1/2 host transport and CLI emission/verification now reconstruct finite evidence without source loading. [Fresh-process and tampering tests](../tests/interchange.rs) preserve exact type trees and separately requested meaning/provenance. The CLI emits the closed observation entry with null type metadata; typed unary exporters retain their own checked trees. Hierarchy, source adequacy and generalized QPE remain separate. See the [development record](releases/v0.2.0.md).

The following is the preserved 0.1.9 finding and acceptance experiment:

**Existing M1 implementation gap, recorded for code-driven work on 2026-09-28.**
The [machine interface](machine-interface-spec.md#portable-finite-ir-and-evidence)
specifies QIRF1/QIRF2, but `emit-ir` and `verify-ir` are unimplemented. Existing
[function evidence](../tests/function_evidence.rs) and
[meaning evidence](../tests/meaning_evidence.rs) are independently checked
inside the Rust API; JSON check/run output is not a portable evidence format.
The desired workflow is the specified, currently unsupported command pair:

```text
qleisli emit-ir <project> --output=<new-file>
qleisli verify-ir <artifact> --against=<independent-request-file>
```

**Author obligation:** automation currently needs an in-process Rust integration
to propose or recheck IR/evidence, and cannot mistake a producer's `verified`
claim for a standalone check against the user's requested meaning.
**Selected direction:** implement X2/X3 through the specified bounded untrusted
decoder and existing exact verifier, without trusting serialized private fields.
**Acceptance:** round-trip the existing source/IR fixtures and all constructors;
verify in a fresh process without the frontend/cache. Mutate root port types,
Unit/pair association, body, phase, source/dependencies and requested meaning;
reject cycles, malformed/deep inputs and aggregate-budget excess. Preserve full
source identity but do not claim that it proves translation adequacy.
**Dependency/migration:** independent M1 slice; QIRF1 precedes QIRF2, hierarchy
requires its own format. Additive commands/types can be PATCH; changing public
Rust constructors or existing format meanings requires separate migration.

### A020-18 — Algorithm trials need actual samples and typed retries

**0.2.0 implementation:** [Fresh sampling](../src/sim/sampling.rs), [typed trials](../src/host.rs) and [validated bounded factor trials](../src/host/factoring.rs) are implemented. The unchanged Grover snapshot now produces samples; the [sampled Shor15 client](../examples/sampled_shor15.rs) reuses the finite order-finding source. [Sampling](../tests/sampling.rs) and [trial](../tests/trials.rs) regressions cover correlations, hidden observations, failure and exhaustion. This resolves the finite host boundary, not M3/M4 algorithm generalization.

The following is the preserved 0.1.9 finding and acceptance experiment:

**Existing M1 implementation gap, recorded for code-driven work on 2026-09-28.**
The [Shor15 host example](../examples/shor15.rs) explicitly iterates over the
entire `run_closed` distribution. The [Grover draft](imaginary-v1/grover.md)
instead needs one fresh execution per attempt, predicate validation and an
exhaustion result. The [selected sampling/trial contract](machine-interface-spec.md#sampling-and-typed-trials)
is specified but unimplemented; enumerating successful simulator branches is
not an implementation of it.

**Author obligation:** currently handwrite sampling and error/retry policy
outside supported Qleisli APIs, or restrict the program to exhaustive reference
analysis. **Selected direction:** X4's fallible trajectory sampler and X5's
typed trial combinator, preserving the current simulator and output contract.
Start with the unchanged [Katas Grover2 trial](../corpus/quantum_katas/grover2/main.qli),
then finite order finding; this does not require sized source.
**Acceptance:** execute all X4/X5 cases: deterministic and correlated outcomes,
reset/discard, feedback, specified RNG words, independent statistical checks,
fresh preparation, first/later acceptance, retries, zero/excessive limits and
injected randomness/runtime/numerical failure. Validate factors and periods;
do not turn execution errors into ordinary retries or hide rejected attempts.
**Dependency/migration:** M1 host slice, needed for R13/M3/M4 and parts of
A020-16; independent of M2. New APIs and commands may be PATCH, while replacing
existing exhaustive results would require a compatibility review.

### A020-19 — General predicates and arithmetic cannot be delivered as tables

**Existing scaling constraint, recorded for code-driven work on 2026-09-28.**
[Finite arithmetic](../stdlib/src/arithmetic.qli) and
[two-bit predicate helpers](../examples/operation_algorithms/oracles.qli)
are useful executed specializations. The [Grover](imaginary-v1/grover.md) and
[Shor](imaginary-v1/shor.md) drafts require reusable constructions: a reversible
predicate `|x,y,0_s> -> |x,y xor f(x),0_s>` and modular multiplication that also
specifies every out-of-residue input. Expanding their whole domains into tables
would keep the algorithm author responsible for exponential generation and
cannot fulfill the selected scalable implementation contract.

**Author obligation:** specialize widths and logic in separate finite source
bodies while the compiler enumerates complete domains; there is no scalable
construction/evidence interface. Current finite computed forms already check
inverse/cleanup obligations, so this is not a missing finite zero-return check.
**Selected direction:** the [M3/M4 decomposition](hierarchical-ir-spec.md#synthesis-without-complete-truth-tables)
uses Boolean DAG synthesis, then add/compare/reduce/uncompute arithmetic, with
joint circuit/evidence binding. **Acceptance:** compare every small-domain case
with independent finite oracles, including noninjective predicates with a
separate XOR target, noncoprime multipliers, x >= N, controlled sign, entangled
references and dirty scratch. For increasing declared sizes, record generation,
IR/proof nodes and checker work; the delivered general construction must not
enumerate all basis inputs. A cache or a larger matrix limit does not pass.
**Dependency/migration:** R06/R09 and M3/M4 after M2's hierarchy/R14. Complete
source/API and proof contracts before implementation; any public interface/IR
replacement needs explicit migration. This is a future generalization obstacle,
not a defect in the supported finite table semantics.

### A020-20 — Core work limits do not isolate source-loading resources

**0.2.0 implementation:** bounded CLI loading and explicit legacy/override migration now implement X6. [Capacity regressions](../tests/source_capacities.rs) check byte boundaries, UTF-8, project/bundle accounting and legacy behavior. Existing Rust loader entry points retain legacy policy. Whole-process CPU/memory/output/filesystem isolation remains an external driver responsibility; the source byte cap alone does not resolve it.

The following is the preserved 0.1.9 finding and acceptance experiment:

**Code-inspection finding for automation preparation, 0.1.9 (2026-09-28).**
The [project loader](../src/frontend/project.rs) discovers project `.qli` files
and reads them with `fs::read_to_string`; its current byte loading is unbounded.
A comment-only large file still consumes initial I/O, UTF-8 decoding and
tokenization resources before the lowering/evidence budgets can protect them.
This follows from the loader path, not a newly executed resource-exhaustion
benchmark. Fixing repeated identity snapshots in A020-10 is a different issue.

**Author/driver obligation:** an unattended generated-source loop needs external
per-job memory/time/input/output limits and filesystem isolation; it cannot
advertise the existing checker work limit as a whole-process resource bound.
Report such driver failures separately from source rejection and preserve the
submitted source. **Selected direction:** implement the already specified
[X6 loader policy](machine-interface-spec.md#source-input-capacities-and-migration):
1 MiB per file and 16 MiB aggregate defaults, bounded reads before allocation,
explicit overrides and `--legacy-source-limits`, with the legacy Rust adapter.
These limits are future defaults, not current guarantees.
**Acceptance:** exact boundary and limit+1 inputs, multibyte UTF-8, many small
files, bundled accounting, overflow, symlink/canonical-path rules and located
path diagnostics without invented character spans. Check the legacy adapter
and documented overrides preserve previously supported source behavior; test
automation termination/output caps separately from compiler capacity tests.
**Dependency/migration:** X6 can be developed independently of M2, but its newly
rejecting defaults require MINOR. Its current absence is an explicit capacity
policy and future automation obstacle, not a newly imposed B019 defect. Do not
silently add these caps to 0.1.x or weaken evidence limits to compensate.

### A020-21 — Mathematical quantum tests require separate host harnesses

**Author obligation:** write and maintain host harnesses to inspect a program's
meaning, report failures by source/parameters and keep examples synchronized.
The desired abstraction removes that plumbing without replacing independent

**Acceptance:** QFT2/3 and reversible arithmetic against independent references;

### A020-23 — Operations have parallel application and description forms

**Observed in the 0.2.0 design review, 2026-09-29;
[#16](https://github.com/MGYamada/Qleisli/issues/16).**

Two surfaces express the same operation concepts:
- **application forms** `adjoint`, `repeat_static` and `qif`, which take
  function names;
- **description constructors** `inverse_op`, `repeat_op`, `controlled_op`,
  `then_op` and `tensor_op`, whose results cannot be applied directly.

`inverse_op(U)(q)` is a parse error, and so is a `qif` arm written as
`repeat_op(2,U)`. Hence the `apply`/`controlled` bridge helpers in the
[amplification](../examples/operation_algorithms/amplification.qli) and
[estimation](../examples/operation_algorithms/estimation.qli) examples.

The two surfaces also disagree on:
- names: `Adjoint`, `adjoint` and `inverse_op` for one concept;
- reading order: `then_op` is diagrammatic, `conjugate_op` algebraic;
- access derivation (A020-09).

**Author obligation:** write bridge helpers, and translate between two
notations for one concept.

**Candidate:** one description language with application `D(q)`, as in the
[shared imaginary notation](language-evolution.md#3-shared-notation-for-imaginary-code).
The old forms become deprecated desugarings.

**Acceptance:**
- rewrite QPE, iterative QPE and amplification without bridge helpers;
- verified IR and evidence are identical;
- reject missing access, captures and aliasing;
- cover T/T† and zero-repeat cases.

**Dependency/migration:** coordinate with A020-04, A020-09, A020-12 and
A020-15. Removing the reserved forms needs a MINOR migration. No syntax is
adopted here.

### A020-24 — Static fold notation cannot carry a pattern

**Observed in the 0.2.0 design review, 2026-09-29;
[#17](https://github.com/MGYamada/Qleisli/issues/17).**

The [shared notation](language-evolution.md#3-shared-notation-for-imaginary-code)
binds `carry state = initial` to a single name. The
[QPE draft](imaginary-v1/qpe.md#visible-algorithm-and-ownership-routing)
therefore packs `(phase, target)` into `pair` and immediately unpacks it. The
[QSVT draft](imaginary-v1/qsvt.md) already writes
`carry (s, q) = (selector, block)`, so the drafts disagree.

**Author obligation:** repack carried owners that a pattern would bind
directly.

**Candidate:** `carry <Pattern> = <Expr>` with a same-shape `yield`, desugared
to the single-name form.

**Acceptance:** once folds are specified, accept both drafts' loops with
pattern carries. Reject shape mismatches, dropped or duplicated carried
owners, and unchecked zero-iteration bodies.

**Dependency:** R04 and the static fold specification. This concerns design
notation only; no current source changes.

### A020-25 — Owner packaging needs hand-written split/join

**Observed in the 0.2.0 design review, 2026-09-29;
[#18](https://github.com/MGYamada/Qleisli/issues/18).**

`split`/`join` emit no gate, yet `Q<(A,B)>` and `(Q<A>,Q<B>)` are distinct types.
- `stdlib/` and `examples/` contain 27 `split(` and 30 `join(` calls.
- [mul2_mod15](../stdlib/src/arithmetic.qli) needs three splits around one line
  of rewiring.
- A tuple pattern cannot destructure `Q<(Bit,Bit)>`.
- Binary `join` cannot pack a flat `Q<(Bit,Bit,Bit)>` without an identity-table
  lift ([explicit layout](../tests/fixtures/tuple_shapes/explicit_layout.qli)).

**Author obligation:** write the functor's structure maps by hand.

**Candidate:** patterns and expected-type packing through `Q` (its strong
monoidal structure), desugared to split/join; or n-ary split/join.

**Acceptance:**
- rewrite the arithmetic, QFT and measurement helpers without explicit
  split/join;
- IR and reference-entangled results are identical;
- reject lost or duplicated owners and leaf permutations.

**Dependency/migration:** related to A020-01. Ownership never implies
separability, and zero-width owners keep their controlled scalar phase.

### A020-26 — Controlled application needs identity arms per type

**Observed in the 0.2.0 design review, 2026-09-29;
[#19](https://github.com/MGYamada/Qleisli/issues/19).**

Controlled U is written `qif(c,q){0=>identity,1=>U}`. The repository has 73
such identity arms and 38 `unitary fn identity` definitions. One of them exists
only for `Q<((Bit, Bit), (Bit, Bit))>` in
[order finding](../examples/order_finding/estimation.qli). A `Q<Bit>` identity
rejects a pair target, and the zero arm cannot be omitted.

**Author obligation:** restate, once per type, an identity that physics already
fixes.

**Candidate:** `controlled(U)(c,q)` via A020-23, or a built-in identity at every
basis type, or an omitted zero arm. Keep two-arm `qif` for multiplexers.

**Acceptance:**
- remove the std and example identity helpers with identical IR;
- controlled U and controlled −U remain distinguished;
- cover zero-width targets.

**Dependency:** A020-12 and A020-23. No syntax is adopted here.

### A020-27 — Diagonal phases require a control/target choice

**Observed in the 0.2.0 design review, 2026-09-29;
[#20](https://github.com/MGYamada/Qleisli/issues/20).**

The controlled S and T gates in [qft2/qft3](../stdlib/src/transforms.qli) are
symmetric diagonals, but `qif` forces a choice of control. A probe with
`apply_contract` confirmed that controlled-S written as `qif(b,c)` and as
`qif(c,b)` are exactly equal, while controlled-T differs.

Diagonal phases can be stated as meanings but can be executed only through
`qif` or a `with_computed` ancilla; the IR monomial step has no such asymmetry.
S itself has no bundled name: it is redefined as `phase_quarter`, and as
`quarter_phase` in 13 files.

**Author obligation:** choose a meaningless control, and rederive S.

**Candidate:** an executable symmetric phase form lowered to monomial steps,
plus a standard `s`.

**Acceptance:**
- rewrite QFT2/3 and compare them exactly;
- reject a wrong sign or power;
- include entangled references.

**Dependency:** A020-28 and the M2 dyadic profile. No new trusted rule.

### A020-28 — Phase exponents are bit tuples

**Observed in the 0.2.0 design review, 2026-09-29;
[#21](https://github.com/MGYamada/Qleisli/issues/21).**

`phase_by` requires `A -> (Bit,(Bit,Bit))` for what is intended as a `Z/8Z`
value, so authors write −1 as `(0,(0,x))`
([oracles](../examples/operation_algorithms/oracles.qli)).
- Left-nested or flat exponents are rejected.
- The nesting differs from `qft3`'s.
- The shape fixes the modulus, whereas the
  [M2 profile](hierarchical-ir-spec.md#first-qpe-profile-and-exact-angles) uses
  canonical dyadic pairs.
- The oracle predicate is written twice.

**Author obligation:** encode phase numbers in binary, following a nesting
convention.

**Candidate:** an exact phase value type (dyadic turns) and a `(-1)^f` meaning
combinator, consistent with the [coefficient-domain note](coefficient-domains.md).

**Acceptance:**
- restate the existing meanings;
- compare all eight ζ8 phases exactly, and π/8 later;
- reject a wrong sign, a wrong power and non-dyadic values.

**Dependency/migration:** existing meanings are public semantics, so the
change is MINOR.

### A020-29 — Basis and classical bits are separate types

**Observed in the 0.2.0 design review, 2026-09-29;
[#22](https://github.com/MGYamada/Qleisli/issues/22).**

`Bit` (`0`/`1`) and `CBit` (`false`/`true`) denote the same set, with no
conversion between them. Basis functions cannot run on measured values; the
[lowering](../src/frontend/compile/lower/mod.rs) reports "basis functions are
used only in basis expressions and with_computed". The
[Grover draft](imaginary-v1/grover.md) needs `eval_basis` just to reuse its own
predicate.

Readout safety already follows from `Q<·>` and the isolated `do`/basis scopes.
Rust uses one `bool`, with `const fn` for compile-time evaluation.

**Author obligation:** duplicate classical logic in two vocabularies.

**Candidate:** one classical bit/word type, with basis functions usable both
coherently and at runtime.

**Acceptance:**
- reuse one predicate and one decoder in both roles;
- reject any unmeasured readout;
- IR is unchanged after literal migration.

**Dependency:** decide before `Bits<n>`/`CBits<m>`. The literal and public API
migration is MINOR.

### A020-30 — Basis-state preparation lacks a unit

**Observed in the 0.2.0 design review, 2026-09-29;
[#23](https://github.com/MGYamada/Qleisli/issues/23).**

Preparing |1⟩ on the order-finding target takes
`join(join(x(init0()),init0()),join(init0(),init0()))`
([main](../examples/order_finding/main.qli)), and a standalone `pure 1` is a
parse error. The Kleisli unit `A -> Q<A>` (prepare |a⟩, an `Iso`) is missing.
The structural operations are also uneven: `discard` accepts every register,
while `init0` and `measure_z` accept only `Bit`.

**Author obligation:** mirror the type tree with gates to prepare or measure a
register.

**Candidate:** `pure a : Q<A>` and register measurement satisfying
`measure(pure a) = a`.

**Acceptance:**
- rewrite the preparations and the QPE measurement with identical
  distributions and IR;
- reject non-basis literals and width mismatches.

**Dependency:** R05, A020-25 and A020-29.

### A020-31 — Exact specifications have two mechanisms

**Observed in the 0.2.0 design review, 2026-09-29;
[#24](https://github.com/MGYamada/Qleisli/issues/24).**

Two mechanisms state the same exact equation:
- `apply_contract` takes a unitary program as its specification
  ([function contracts](../examples/function_contracts/main.qli));
- `meaning`/`bind_op` use `phase_by` or `permutation_by`
  ([operation contracts](../examples/operation_contracts/main.qli)).

Meanings are monomial only, so the QFT cannot be one. Meanings also require
unary basis functions, unlike `with_computed`. A probe showed that a plain
provider already satisfies `Op<A,M>` when its operator equals M, so what
`bind_op`'s retained identity adds is not visible in source.

**Author obligation:** choose between two vocabularies for one exact equation.

**Candidate:** one specification form and one binding mechanism, with
`apply_contract` as desugaring.

**Acceptance:** express both examples and a QFT2 specification in one
mechanism, with identical results.

**Dependency:** FC-CACHE and meaning evidence are unchanged. No new trusted
rule.

### A020-32 — Multi-parameter predicates are implicitly left-folded

**Observed in the 0.2.0 design review, 2026-09-29;
[#25](https://github.com/MGYamada/Qleisli/issues/25).**

The `with_computed` predicate domain folds parameters into binary pairs
([lowering](../src/frontend/compile/lower/mod.rs),
[certified form](../src/frontend/compile/lower/certified.rs)). For a
three-parameter predicate:

| Predicate form | Register | Result |
| --- | --- | --- |
| three parameters | `Q<(Bit,Bit,Bit)>` | rejected: "expected `(Bit,Bit,Bit) -> Bit`, found `((Bit,Bit),Bit) -> Bit`" |
| three parameters | `Q<((Bit,Bit),Bit)>` | accepted |
| unary pattern | `Q<(Bit,Bit,Bit)>` | accepted |

This contradicts both the [tuple rule](tuple-shapes.md) and the argument-list
rule of the [type contract](type-system.md).

**Author obligation:** know about a hidden associator, and three conventions
for one concept.

**Candidate:** one convention (a unary product parameter, or n parameters as a
flat product), with a migration diagnostic.

**Acceptance:**
- all std and example predicates keep identical tables and IR;
- the probes follow the chosen rule.

**Migration:** MINOR.
