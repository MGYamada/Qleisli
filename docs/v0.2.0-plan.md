# 0.2.0: finite interfaces and the Lean kernel foundation

Status: **release scope finalized; publication requested by the user on 2026-09-29**.
The original 2026-09-28 plan targeted shared sized QPE/QFT. The user now moves
the four remaining implementation areas to [0.2.1](v0.2.1-plan.md), retaining
migration and release validation as the remaining 0.2.0 work. This supersedes
the earlier assignment of common QPE and H1–H5 to 0.2.0; it does not complete
or weaken those feature gates. The [decision dossier](decisions/2026-09-27-v1-path.md)
and [development record](releases/v0.2.0.md) preserve the original adoption
and executed checkpoints.

The baseline remains product 0.1.9, commit
`3c19c7669b5b14b738bceaa5f3eff18f92e2190e`. Cargo and both Lean packages remain
at 0.2.0 for this foundation release. Subsequent development selects
[0.2.1](releases/v0.2.1.md). The [release record](releases/v0.2.0.md#release-validation-and-publication)
separates final validation from tagging, push and publication.

## Deliverable and scope

Ship the implemented finite language and host interfaces, together with the
experimental Lean kernel and its existing component proofs:

* Arity-preserving tuples and the consolidated [type contract](type-system.md),
  with explicit migration from left-associated tuple sugar. Follow Rust when
  type or ownership discipline is uncertain, retaining stated quantum differences.
* The [0.1.9 follow-up review fixes](reviews/v0.1.9-followup.md), including
  shared exact work accounting, finite transform comparison and bare-CR rejection.
* Finite QIRF1/2 emission and fresh-process verification against independently
  requested contracts, trajectory sampling, typed trials and bounded loading
  under [X2–X6](machine-interface-spec.md). Existing `run` remains exhaustive.
* The Mathlib-free Lean runtime, source/declaration audits, independent native
  tests and completed component proofs for layouts, phases, QFT/QPE and the
  supported hierarchical derivations. Preserve their exact premises and limits.
* Code-driven source records, counterexamples, the fixed trust boundary and
  adopted future plans, without presenting desired syntax as executable.

Production finite acceptance remains Rust-authoritative. All three external
hierarchical schema entries remain disabled. The experimental components do
not constitute a production hierarchical verifier, reusable sized QPE or the
complete Qleisli Soundness Theorem. Existing implementations and proofs remain
in the tree and must pass their normal validation; this split removes no checks.

## Release acceptance

1. Complete compatibility and migration review for the changes actually shipped:
   tuple shape/public AST and metadata, source byte policy, exact work limits,
   finite transform capacities and bare-CR handling. Keep documented finite
   Rust/IR entry points and explicit legacy byte-loading options.
2. Align the README, language/API documentation, contract ledger, generated
   status and release notes with this finite production scope and the separate
   experimental proof scope. Keep unsupported hierarchy/schema paths disabled.
3. Validate the final candidate under the [release checklist](versioning.md#release-records-and-validation):
   primary and minimum Rust toolchains, formatting/all-target tests/Clippy,
   existing corpus and examples, documentation and copyable references, pinned
   Lean 4.30.0 builds/axiom audits, runtime policy/native replay, component
   registry and independent regression suites, and clean distribution/license
   checks. Record actual results, platform exclusions and skipped work precisely.
4. Record RC/final candidate validation and the exact checked commit before
   separately authorized tagging, push and publication. Existing checkpoint
   results alone do not close the final release gate.

Limit further 0.2.0 implementation to fixes needed to validate this shipped
scope. Full hierarchy semantics, external production binding, sized source
and shared standard components, and hierarchy execution/integrated H1–H5
validation belong to [0.2.1](v0.2.1-plan.md). In particular, the H1–H5 work
formerly bundled with release validation moves with its feature, rather than
remaining a hidden 0.2.0 requirement.

## Compatibility and continuing work

The implemented tuple/API and capacity/lexical changes justify the 0.2.0 MINOR
boundary. The 0.2.1 target is for compatible additions: preserve the published
0.2.0 AST, IR, evidence, CLI and Lean interfaces, using separate successor APIs
and explicit adapters where needed. If a required change is incompatible,
select 0.3.0 with migration under the existing [version policy](versioning.md);
this scheduling decision grants no incompatible PATCH exception.

The [M0–M5 ordering](v0x-roadmap.md), R14 prerequisite, code-driven method,
v0.5.0 Soundness Theorem and v1 Physical Realizability Theorem remain unchanged.
QLT remains an independent later work stream. The **2026-10-04 JST** checkpoint
evaluates hierarchy/proof/source readiness for the continuation, not a release date.
