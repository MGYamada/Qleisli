## Status

Design issue for **Qleisli 0.3.0**.

Related:
- #16 operation representation unification
- #19 controlled application
- #27 static operator language
- A020-09 capability derivation
- current M1 `Apply` / `Adjoint` / `Controlled` constraints

## Problem

Qleisli correctly distinguishes:

> the mathematical existence of an inverse/controlled operator

from:

> having a verified implementation/access path that the compiler is allowed to use.

Current M1 exposes capabilities such as:

```text
Applicable(U)
Adjointable(U)
Controllable(U)
```

but their derivation rules are not yet a complete language-level calculus.

Some constructed descriptions can expose capabilities that the underlying provider does not expose directly. This is semantically meaningful and must not remain an implementation accident.

## Goal

Define a small compile-time judgment such as:

```text
Γs ⊢ U : Op<A>
Γs ⊢ capability(U, Apply)
Γs ⊢ capability(U, Adjoint)
Γs ⊢ capability(U, Controlled)
```

with explicit derivation rules for operation constructors.

## Questions to decide

1. Which base providers grant `Apply`?
2. Which grant `Adjoint`?
3. Which grant `Controlled`?
4. Does a transparent ordinary circuit automatically grant more capabilities than an opaque external provider?
5. What does `adjoint(U)` require and expose?
6. What does `controlled(U)` require and expose?
7. What does `power(U,n)` require and expose, especially for `n=0`?
8. What capabilities do `then(U,V)` and `tensor(U,V)` expose?
9. Can capability derivation depend on semantic evidence such as unitarity or phase?
10. How are capabilities retained through `Op<A,M>` refinement?
11. Can capabilities be explicitly supplied by external evidence?
12. How are unavailable capabilities diagnosed?

## Core principle

> **Unitarity is a semantic fact; access is an implementation capability. One does not automatically imply the other.**

Similarly:

> **Controlled access must retain exact phase.**

A backend/compiler must not manufacture a controlled implementation merely from channel equality or an arbitrary black-box apply capability.

## Candidate structure

Separate three concepts:

- **meaning**: what operator the object denotes;
- **implementation identity/evidence**: what concrete provider realizes it;
- **capability set**: which transformations/applications are justified for that provider.

Then compile-time constructors transform all three in checked ways.

## Non-goals

This issue does not make operations runtime first-class.

It does not assume every unitary can be efficiently inverted or controlled.

It does not permit capability inference from approximate numerical coincidence.

## Acceptance criteria

1. Publish inference rules for every enabled static operation constructor.
2. Cover transparent source-defined operations, sealed gates, and opaque/certified providers.
3. Preserve phase-sensitive controlled cases.
4. Reject direct application when only controlled access exists unless a constructor explicitly changes the capability object.
5. Cover zero powers and zero-width targets.
6. Keep capability derivation independent of surface legacy syntax.
7. Show QPE controlled powers use the same calculus as ordinary clients.
8. Bind capabilities to exact implementation identity and evidence.

## Design intent

The capability system is not incidental API metadata.

It is the compile-time logic that answers:

> **What transformations of this verified operation are we actually entitled to perform?**

## 2026-10-07 capability naming decision

Capability predicates use adjective forms:

```text
Applicable(U)
Adjointable(U)
Controllable(U)
```

Operator constructors remain distinct:

```text
adjoint(U)
controlled(U)
```

This prevents `Controlled(U)` from looking like a constructed controlled operator and `Adjoint(U)` from looking like the mathematical adjoint itself.


## 2026-10-07 adjoint/inverse decision

The general constructor is:

```text
adjoint(U)
```

and requires `Adjointable(U)`.

Do not use `inverse(U)` as the general constructor. For an isometry, the adjoint exists as a linear map but need not be a two-sided inverse. The identifier `inverse` is reserved for a future API whose two-sided inverse law is explicitly established.

For a unitary, `adjoint(U)` equals the mathematical inverse.
