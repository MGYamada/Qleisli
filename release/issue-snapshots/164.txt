## Problem

Future ecosystem features may introduce foreign execution paths such as:

```text
extern operation
host callback
runtime plugin
device-native call
foreign qrate/provider
backend extension
hardware service invocation
```

Any such path can potentially hide unbounded or unknown behavior:

- dynamic qubit allocation;
- arbitrary loops/retries;
- hidden measurements;
- target-dependent workspace;
- unbounded gate sequences;
- uncontrolled host/device interaction.

If foreign execution can occur inside a Resource Safety-certified program without a checked contract, the theorem becomes vacuous at exactly the extension boundary where the ecosystem is most open.

## Required 0.3.0 rule

Foreign behavior has only two legal positions:

### A. Outside the Resource Safety theorem boundary

The host/runtime may invoke external functionality, but Qleisli makes no quantitative theorem claim across that call.

### B. Re-enter through a checked operation contract

A foreign implementation may participate inside the theorem boundary only after it is represented as a finite checked operation/provider contract that includes the resource evidence required by the selected target/cost model.

There is no third category of "trusted because external".

## Callbacks

Runtime callbacks from the verified quantum core into arbitrary host code should be forbidden in the initial profile unless the callback itself is statically represented by a closed checked provider.

In particular, a callback must not be able to decide dynamically to allocate more quantum resources or generate an unbounded circuit under an already-issued certificate.

## Plugins and compiler extensions

Plugins may propose:

- source;
- IR;
- implementations;
- resource certificates;
- target mappings.

They may not extend semantic or Resource Safety authority merely by being installed.

Their outputs pass through the same independent checks as any other producer.

## Device-native instructions

A native device instruction is not automatically a zero/constant-cost primitive.

Its cost/resource contract must be explicit in the target model, including any hidden workspace, measurements, feed-forward, duration/depth semantics, or other selected metrics.

## FFI and ownership/effects

Any future FFI crossing must also preserve:

- linear ownership;
- effect classification;
- clean/dirty obligations;
- hidden measurement accounting;
- implementation identity/provenance.

A resource certificate cannot compensate for an otherwise unverified semantic/effect boundary.

## Non-goals

This issue does not require:

- implementing an FFI in 0.3.0;
- forbidding host orchestration;
- trusting plugins;
- modeling network latency or hardware queue time by default;
- one universal foreign ABI.

It fixes the theorem boundary before such features are added.

## Acceptance criteria

- [x] The Language Reference states that arbitrary foreign execution is outside quantitative Resource Safety unless reintroduced through a checked finite contract.
- [x] Runtime callbacks cannot bypass static resource certification.
- [x] Plugins/compiler extensions cannot add Resource Safety authority by installation alone.
- [x] Foreign/device-native providers require explicit target/resource contracts.
- [x] Hidden workspace/measurement/feed-forward costs remain visible to the selected resource model.
- [x] Foreign producers' certificates remain untrusted until independently validated.
- [x] Ownership/effect/cleanup obligations still apply across any admitted foreign provider boundary.
- [x] Unknown or unbounded foreign behavior fails closed for Resource Safety certification.
- [x] Future FFI design must explicitly declare whether each call is inside or outside the theorem boundary.

## Design principle

> **Foreign code may extend the ecosystem, but it may not create an unbounded hole inside a finite resource theorem.**
