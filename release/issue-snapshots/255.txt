## Problem

Qleisli editions identify constitutional regimes, not syntax generations.

An edition identifies the ratified constitutional framework and its continuing obligations. Release/formalization state identifies the current grammar, implementation, acceptance judgments, and semantic realization within that framework. Following #137, explanatory coordinates include:

```text
Constitution_e
Jurisdictions_e
Ledger_e,t

Accepted_e,t(P)
Meaning_e,t(P)
RealizationAccepted_e,t(P, target, artifact, evidence)
```

These are explanatory indices, not fixed constitutional theorem names or a requirement to freeze acceptance and semantics for an entire edition.

If a `.qli` or `.qlt` source can omit its edition and silently inherit the compiler's current/default/latest edition, then the same source tree may later be interpreted under a different constitutional regime without any source or manifest change.

That is unacceptable for a language whose guarantees are edition-indexed.

The manifest therefore needs to bind every ordinary Qleisli project explicitly to one constitutional edition.

## Normative rule

For every ordinary Qleisli source tree or qrate containing `.qli` and/or `.qlt` source, a schema-2 `Qargo.toml` **MUST explicitly declare `edition` in `[qrate]`**.

For example:

```toml
schema-version = 2

[qrate]
edition = "2026"
```

The central invariant is:

> **A Qleisli source tree must never silently change the Constitution under which it is interpreted.**

Equivalently:

> **Compiler release selects the implementation; edition selects the constitutional regime.**

## 1. Missing edition is a hard error

For a normal package/qrate build, check, test, or QLT invocation:

```text
Qargo.toml contains .qli/.qlt sources
        +
edition absent
        ↓
hard error
```

This must not be a warning.

The compiler/qlirgo must not silently insert `edition = latest`, `edition = current`, `edition = toolchain-default`, or any equivalent floating interpretation.

## 2. Floating editions are forbidden

The manifest must name a concrete edition.

Forms equivalent to `latest`, `current`, or `*` must not exist.

The same project checked years later must still request the same constitutional edition unless the manifest is explicitly changed.

## 3. `.qlt` is covered by the same rule

QLT is not exempt.

Tests must not be interpreted under a different or implicit edition from the source they are asserting properties about.

Therefore:
- `.qli` is edition-bound;
- `.qlt` is edition-bound;
- a qrate-level QLT suite inherits the explicit `[qrate].edition` unless a future specification introduces an equally explicit, non-floating override;
- ordinary test tooling must never select an edition implicitly.

## 4. Edition and toolchain version are distinct coordinates

The manifest model must distinguish:

```text
toolchain/compiler version
    = which implementation is used

edition
    = which constitutional regime and continuing obligations are requested
```

Many compiler releases may implement one edition. Those releases may change syntax, types, or tooling under an explicit release compatibility and migration policy. Such changes do not select another edition or amend the Constitution by themselves.

Updating from one compiler version to another must **not** by itself migrate the project to a new edition.

Likewise, declaring edition `2026` does not uniquely pin a compiler patch release.

This concretizes the release/edition distinction tracked in #137.

## 5. Edition migration must be explicit

Changing edition is a semantic/constitutional migration, not routine dependency drift.

A migration from `edition = "2026"` to `edition = "2029"` must require an explicit manifest edit or an explicit migration command whose result includes that manifest edit.

Tooling may assist migration, but it must never perform an edition change merely because a newer toolchain is installed.

The manifest diff should make the constitutional transition reviewable in Git history.

## 6. The effective edition must reach the authoritative acceptance path

The edition field must not remain frontend-only metadata.

Conceptually:

```text
Qargo.toml
   edition = e
        ↓
frontend / project loading
        ↓
canonical artifact / Core metadata
        ↓
authoritative verifier / acceptance
        ↓
Accepted_e,t / Meaning_e,t under Constitution_e and its applicable obligations
```

The authoritative acceptance path must bind the requested constitutional edition together with the release/profile and checker identity whose current normative rules it executes. Declaring an edition alone does not identify a grammar or a complete acceptance predicate.

A frontend must not be able to claim one constitutional edition while the verifier silently checks another.

## 7. Dependencies do not redefine the root edition

Ordinary qrate dependencies may declare their own compatible edition metadata according to the package specification, but dependency resolution must never silently change the root project's edition.

If a dependency graph is incompatible with the root edition, resolution/checking should fail with a diagnostic rather than migrating the root project.

The exact cross-edition dependency compatibility policy may be specified separately; the invariant here is that **dependency selection cannot mutate constitutional meaning implicitly**.

## 8. Standalone / snippet tooling

The normal Qleisli project model should require `Qargo.toml`.

If future tooling intentionally supports isolated source snippets without a manifest, that mode must still receive an edition **explicitly** (for example by a required CLI/API parameter).

It must not fall back to a floating current/latest edition.

Such a mode is tooling convenience, not an exception to the constitutional binding rule.

## 9. Diagnostics should teach the rule

A missing-edition diagnostic should explain why the field is mandatory, for example:

```text
error: Qleisli edition is not declared

This source tree contains .qli/.qlt source, but its schema-2 Qargo.toml
does not declare `qrate.edition`.

Qleisli editions identify constitutional regimes; the compiler will
not choose one implicitly.

Declare the edition explicitly:

    schema-version = 2

    [qrate]
    edition = "2026"
```

This aligns compiler diagnostics with the general principle that errors act as part of the language harness.

## 10. Reproducibility consequence

With an explicit edition, a repository records both source/package history and constitutional semantic identity.

A future toolchain may stop supporting an old edition as an implementation-policy matter, but it must never reinterpret old source as a newer edition merely to keep compiling it.

This preserves the distinction from #137:

- ratified constitutional text and recorded ledger guarantees retain their historical identity and meaning under #137 and the applicable constitutional rules;
- current formal realizations, release compatibility, and implementation support may evolve separately without silently changing the requested edition.

## Acceptance criteria

- [ ] The Language/Package Reference states that ordinary `.qli` / `.qlt` projects MUST declare `[qrate].edition` in a schema-2 `Qargo.toml`.
- [ ] Missing edition is a hard error, not a warning.
- [ ] No implicit default/current/latest edition exists for ordinary qrate builds.
- [ ] Floating edition values are forbidden.
- [ ] `.qlt` is explicitly covered by the same constitutional binding rule as `.qli`.
- [ ] Updating the Qleisli toolchain does not automatically change the project edition.
- [ ] Edition migration requires an explicit manifest change.
- [ ] The selected edition is propagated to the authoritative Core/verifier/acceptance boundary.
- [ ] The verifier cannot silently check a different edition from the manifest-selected one.
- [ ] Dependency resolution cannot silently mutate the root project's edition.
- [ ] Any future manifest-free snippet mode still requires an explicit edition parameter.
- [ ] Diagnostics explain that edition identifies the constitutional regime rather than a grammar generation.
- [ ] Conformance tests cover missing, invalid, floating, mismatched, and explicitly migrated editions.
- [ ] #137 is updated/cross-referenced so its open question “Does source code declare its edition?” is resolved normatively.
