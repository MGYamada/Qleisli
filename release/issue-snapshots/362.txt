## Problem

`Kernel::check` sends the QLV1 packet to the Lean checker. On acceptance, Rust re-parses the same bytes with its own independent decoder (`decode_native` / `RawProgram::read` in `src/interchange/mod.rs`) to build the `AcceptedProgram` that simulation, export and emission consume.

Lean's success facts (`Protocol.Validity.check_acceptance`, `check_ownershipSafe`) are about the artifact as decoded by Lean's own `Qirf.read`. At runtime, nothing checks that the `RawProgram` Rust decoded is the program Lean checked.

Existing coverage:

- `TRUSTBOUNDARY.md` and #276 record "decoder correspondence" as an explicit assumption.
- #288 added bounded accepted-artifact round-trip tests over fixtures.

Neither binds an individual accepted artifact.

The JSON layer is already aligned: duplicate keys are rejected on both sides, only canonical unsigned integers are accepted, and depth is bounded. The remaining gap is at the QIRF structure layer. A field that the two readers interpret differently would yield an accepted artifact whose executed meaning differs from the checked one, with no error. Examples include a default or optional field, an ignored field, index or ordering conventions, and tag aliasing such as the retained historical `"iso"` tags.

This affects the claim that "Lean alone issues accepted handles". Today the handle certifies the bytes, not the decoded program that actually runs.

## Proposal

Bind the decoded program to the decision, failing closed on any divergence, without trying to prove the Rust decoder. Two possible designs:

1. **Comparison inside the trusted side.** Rust decodes the proposal before submission and appends its canonical re-encoding of the decoded program and evidence graph to the packet. Lean re-encodes its own `Qirf.read` result canonically and accepts only if the two are byte-equal.
2. **Digest echo.** The native accepted reply carries a digest of Lean's canonical decoded form. Rust computes the same digest from its decoded view and rejects before constructing `AcceptedProgram` if they differ.

Option 1 keeps the comparison on the Lean side and needs no hash implementation in the Mathlib-free kernel.

Either option changes the wire protocol. `runtime::response` rejects trailing lines and the request packet is length-framed, so the change must be an explicit protocol version bump.

## Acceptance criteria

- [x] The canonical decoded form is specified once, with shared test vectors, and both sides implement it.
- [x] Every native mode that results in an execution view (finite, hierarchy, contract/instrument paths) binds the decoded program as above. A mismatch rejects with a distinct code.
- [x] Negative tests: a deliberately divergent Rust decoding, or a mutated canonical form, is rejected even though Lean accepts the raw artifact.
- [x] The old protocol version is rejected after the bump; there is no compatibility fallback.
- [x] `TRUSTBOUNDARY.md` states precisely which decoder-correspondence assumption remains, if any.
