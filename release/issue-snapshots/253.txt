## Goal

Document, before the 0.3.0 language boundary is frozen, which parts of the Qleisli language and ecosystem are expected to be **inferable by an LLM with no prior Qleisli knowledge**, and which parts are **Qleisli-specific concepts that must be explicitly discoverable**.

The design goal is not:

> make every name look familiar.

It is:

> **An LLM with generic programming knowledge but zero Qleisli-specific prior should be able to reconstruct the ecosystem wherever inference is intended, and should encounter an explicit discovery path wherever inference is impossible or unsafe.**

This boundary is part of the language/tooling documentation contract.

## Motivation

Qleisli is deliberately structured so that a coding agent can begin with ordinary classical programming priors, make predictable mistakes, and use the language/tooling response to recover the Qleisli model.

Examples of intentionally inferable ecosystem structure include:

- Cargo → qargo
- crate → qrate
- clippy → qlippy
- formatter conventions → qlifmt
- documentation tooling conventions → qlidoc
- classical/quantum syntax boundaries such as `if` / `qif`, `for` / `qfor`, and `match` / `qmatch`

The point is not superficial spelling similarity. The point is that repeated structure lets an agent infer the **classical/quantum boundary rule** and transfer it to previously unseen parts of the ecosystem.

By contrast, important Qleisli-native tools such as:

- **QLT**
- **QDB**
- **QCP**

cannot be reconstructed reliably from generic Rust/C/Cargo prior alone. They are closer to the semantic core of the Qleisli ecosystem, yet their roles must be **discovered**, not guessed.

The documentation must therefore draw the boundary explicitly.

## Core distinction

### 1. Zero-prior inferable domain

A component belongs here only when a generic coding agent can reasonably infer its role from stable ecosystem structure, naming, nearby source, or deterministic diagnostics.

Requirements:

- inference should lead to the correct conceptual role, not merely the correct spelling;
- predictable classical habits may fail, but the failure must expose the Qleisli boundary rather than dead-end;
- diagnostics should name the canonical Qleisli counterpart where appropriate;
- repeated naming/structural rules should remain consistent enough to transfer to unseen components;
- documentation should state the intended inference path.

Examples: `qargo`, `qrate`, `qlippy`, `qlifmt`, `qlidoc`, and the q-prefixed classical/quantum surface boundary where specified elsewhere.

### 2. Explicitly discoverable Qleisli-native domain

A component belongs here when no reasonable generic prior determines its meaning.

Requirements:

- do not pretend it is inferable by giving it a misleading classical analogue;
- provide a stable first discovery path from the ordinary CLI/docs/toolchain;
- state what problem the component solves before requiring detailed knowledge of its protocol;
- make relationships among the native components explicit;
- unknown-tool or help flows should point agents toward the canonical description.

Primary examples: **QLT, QDB, and QCP**.

These tools may be central precisely because they are Qleisli-specific. Centrality does not imply zero-prior inferability.

## Stdlib and source-level inspectability

The primitive/derived boundary in #167 is part of this design.

When a derived stdlib abstraction is unfamiliar, the fallback should be:

```text
recognize / infer usage
        ↓
inspect its type/signature
        ↓
read the ordinary checked .qli implementation
        ↓
follow the primitives and language rules it uses
```

Thus ordinary derived stdlib code being written in `.qli` is not merely aesthetic consistency. It preserves an **inspectable recovery path** for agents that do not already know the abstraction.

The documentation should distinguish:

- inferable by ecosystem prior;
- inspectable from ordinary `.qli` source;
- explicitly discoverable Qleisli-native concept;
- sealed primitive / external authority that requires specification rather than source-level reconstruction.

## Failure modes to forbid

The most dangerous category is neither clearly inferable nor clearly native, but **apparently inferable with the wrong semantics**.

Document and audit against:

- classical false friends whose names suggest a stronger analogy than the semantics permit;
- tools that look like q-prefixed mirrors but have fundamentally unrelated roles;
- diagnostics that report only an unknown name without exposing the intended boundary;
- native Qleisli concepts that are documented only after the user somehow already knows their names;
- stdlib abstractions whose behavior cannot be recovered from either source or a canonical contract;
- hidden ecosystem conventions that require repository-specific folklore.

A zero-prior agent should either infer correctly or be routed to discovery. It should not be rewarded for a plausible but semantically wrong guess.

## Acceptance criteria

- [x] 0.3.0 documentation defines **zero-prior inferable** and **explicitly discoverable** as distinct design categories.
- [x] First-party language/ecosystem concepts are classified, with QLT/QDB/QCP explicitly treated as Qleisli-native discovery targets.
- [x] The docs state that superficial code/name similarity is not sufficient; the intended semantic role must be recoverable.
- [x] Inferable components have a deterministic correction path from predictable classical mistakes.
- [x] Non-inferable components have a canonical discovery path that does not require prior knowledge of their names.
- [x] The stdlib `.qli` source path is documented as a fallback for unfamiliar derived abstractions.
- [x] Sealed primitives and external semantic authority are separated from source-level reconstruction.
- [x] Naming guidance forbids misleading pseudo-analogues / semantic false friends.
- [x] The issue is cross-linked from the Language Reference and relevant diagnostics/stdlib architecture docs.
- [x] Future first-party ecosystem additions are expected to declare which side of this boundary they occupy.

## Design principle

> **Qleisli should not require an LLM to know Qleisli before it can learn Qleisli.**

And equally:

> **What can be inferred should be reliably inferable; what cannot be inferred should be reliably discoverable.**
