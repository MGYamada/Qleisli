## Status

Surface-language design issue for **Qleisli 0.3.0**.

#41 defines the semantic/name-resolution problem. This issue is narrower: define a pleasant module/import/visibility surface that **erases to fully qualified deterministic names**.

## Motivation

As stdlib and qrates grow, source needs ordinary organizational tools:

```text
std::transform
std::arithmetic
std::code
...
```

Authors should not have to write fully qualified paths everywhere, but import convenience must not create semantic ambiguity.

## Design principle

> Modules organize names; they do not create runtime semantics.

Import and visibility syntax should be resolved completely before later elaboration/Core verification.

## Candidate surface

Illustrative only:

```qli
mod fourier;

use std::phase::controlled_phase;

pub fn qft[...] (...) { ... }
```

Potential minimal visibility:

```text
private    -- default
pub
```

A richer `pub(qrate)` / `pub(super)` model can be deferred unless there is an immediate qrate-management need.

## Required lowering rule

```text
module path
    ↓
canonical fully qualified symbol identity

use/import
    ↓
local alias in the resolver only

visibility
    ↓
compile-time accessibility check

resolved call/type/Meaning name
    ↓
same fully qualified identity used by elaboration/evidence
```

Nothing about an imported name bypasses ordinary static typing, ownership, capability, Meaning or verification checks.

## Initial restrictions

Prefer a small deterministic profile:

- explicit imports;
- no glob imports initially;
- no implicit prelude except a deliberately specified tiny one;
- no ambiguous fallback search;
- no runtime module initialization;
- no import-time side effects;
- no source-order-dependent resolution.

## Questions to decide

1. File-to-module mapping.
2. Absolute path root and `std::` / qrate paths.
3. Whether `use x as y` is needed in 0.3.0.
4. Minimal visibility vocabulary.
5. Re-export policy.
6. Cyclic module handling.
7. Import collision diagnostics.
8. Whether modules and qrates share the same namespace root.
9. How canonical symbol identity is retained in evidence and diagnostics.

## Relationship to #41

#41 remains authoritative for:

- namespace partitioning;
- shadowing;
- declaration-kind resolution;
- ambiguity rules.

This issue should not duplicate those semantics.

Instead:

> #41 answers **which declaration a name denotes**; this issue answers **how authors conveniently spell and expose that declaration across files/modules**.

## Non-goals

- no dynamic loading;
- no module constructors;
- no import side effects;
- no package solver in the language;
- no qlirgo/qrate dependency-resolution semantics here.

## Acceptance criteria

- [x] a small multi-file stdlib example resolves to canonical qualified identities;
- [x] explicit imports are pure resolver sugar;
- [x] private items cannot be accessed externally;
- [x] import collisions reject deterministically;
- [x] evidence/cache identity does not depend on local import aliases;
- [x] no module construct reaches canonical Core as a runtime operation;
- [x] the Language Reference specifies modules as frontend/name-resolution structure.

## Design intent

Qleisli needs namespace ergonomics early because the stdlib is part of the language's teaching surface.

But this should remain one of the cheapest features semantically:

> **Good module syntax should disappear completely by the time Core is verified.**
